# Журнал изменений для обновляющего агента

Новые версии сверху. У каждой версии — раздел «Как обновить приложение»: шаги, которые агент выполняет в приложении, подключившем набор `@ykurilov/remontnik-*`.

## 0.1.10

Прокси eval считает вход из кэша поставщика по его цене.

- **Прокси eval больше не завышает расход на входе из кэша.** Раньше весь вход шёл по цене `input`, даже если поставщик взял его из кэша. Кэш стоит в десятки раз дешевле. У разговоров с длинным общим началом (системный промпт, история) списание выходило в разы больше настоящего. Eval упирался в долю случая и прерывался: «запрос не влез в бюджет». Живой замер, DeepSeek напрямую: 7936 из 8178 токенов входа из кэша. Прокси списывал $0.002477, а с ценой кэша списывает $0.000145. Ответы OpenRouter с готовой ценой (`usage.cost`) и раньше считались верно.
- **Цена входа из кэша у модели — `cachedInput`** в `checks.eval.providers[].models`, долларов за миллион токенов, как `input` и `output`. Дороже `input` быть не может: `check-config` отвечает «cachedInput — цена входа из кэша — не может быть дороже input». Кэш читается из `usage` всех форматов: DeepSeek, OpenAI-совместимого чата и OpenRouter, `responses`, Anthropic, Gemini.
- **Нет `cachedInput`, а кэш в ответе есть** — вход из кэша считается по `input`, то есть с запасом. Журнал врача раз за прогон на модель пишет: `[прокси eval] … у модели <модель> нет цены cachedInput: вход из кэша посчитан по цене input, расход завышен — впишите cachedInput в eval.providers[].models`. Готовая цена поставщика (`usage.cost`) важнее любых цен из настройки.
- **OpenRouter со своим ключом поставщика (BYOK).** К `usage.cost` теперь прибавляется `cost_details.upstream_inference_cost`: раньше в учёт шла только доля OpenRouter.
- **Засчитанная бронь — в журнал с причиной.** Если в ответе нет `usage`, поток оборвался, вышел тайм-аут или ответ больше предела, журнал врача пишет причину и сумму: `… в ответе поставщика нет usage — засчитана бронь $0.0049`, `… ответ поставщика оборвался: … — засчитана бронь $…`.

### Как обновить приложение

Все пакеты набора — `0.1.10`; менялись врач и `core` (схема настройки: поле `cachedInput`). Пакеты набора в приложении поднять до `0.1.10`: иначе тип настройки в `remontnik.config.ts` не знает `cachedInput`.

1. Обновить врача: на сервере перевести клон Ремонтника на метку новой версии и пересобрать (`docker compose -f deploy/compose.remontnik.yml up -d --build`).
2. В `remontnik.config` вписать `cachedInput` каждой модели в `checks.eval.providers[].models`, у которой поставщик кэширует вход. Цену взять у поставщика: «cache hit» у DeepSeek, `input_cache_read` в списке моделей OpenRouter. Пример записи:

   ```json
   "models": {
     "<модель>": { "input": 0.3, "output": 1.2, "cachedInput": 0.03 }
   }
   ```

   Для моделей OpenRouter поле не обязательно: прокси берёт готовую цену ответа. Но если OpenRouter её не прислал, без поля кэш посчитается по `input`.
3. `evalUsdPerCase` менять не нужно: прерывание шло от завышенного учёта, а не от малой доли.
4. Проверить настройку: `remontnik-doctor check-config`. После прогона eval в журнале врача не должно быть строк «нет цены cachedInput».
5. Случай, оборвавшийся на «запрос не влез в бюджет», лечить заново после шагов 1–2: `remontnik-doctor case <номер> retry --by owner` (`--force` не нужен: правки и выкатки не было).

## 0.1.9

Журнал ошибок прокси eval и подсказка, когда клиент модели идёт мимо него.

- **Журнал прокси eval.** Раньше прокси молча отвечал `502` или `500`, и сбой eval нельзя было разобрать. Теперь отказы прокси, ответы поставщика с ошибкой и сбои соединения пишутся в журнал врача: `[прокси eval] POST /<поставщик>/chat/completions: поставщик ответил 503`, `…: поставщик не ответил: fetch failed: ECONNREFUSED …`, `…: 403 модели нет в списке …`. Пропуска прогона, строки запроса, ключей, значений `upstreamHeaders` и тел в журнале нет.
- **Заметка, когда eval идёт мимо прокси.** Если сценарии сломались (`stand_broken`), а к прокси за прогон не пришло ни одного запроса, в итоге проверки и отчёте врача — заметка «к прокси eval не пришло ни одного запроса — клиент модели в eval идёт мимо `<baseUrlEnv>`». Так бывает, когда клиент модели в eval (например, персонаж) создан без адреса из `baseUrlEnv`: в сети проверок без интернета он падает на сетевом сбое, а библиотека называет его `overloaded`.
- **Документы:** каждый клиент модели в eval — агент, персонаж, судьи — берёт адрес из `baseUrlEnv` (`docs/configuration.md`, `checks.eval`).

### Как обновить приложение

Все пакеты набора — `0.1.9`; менялся только врач, `watch` и `core` поднимать не обязательно, но версии набора держим одинаковыми.

1. Обновить врача: на сервере перевести клон Ремонтника на метку новой версии и пересобрать (`docker compose -f deploy/compose.remontnik.yml up -d --build`). Настройку менять не нужно.
2. Проверить код eval приложения: каждый клиент модели (агент, персонаж, судьи) берёт адрес из переменной `baseUrlEnv` и ключ из `keyEnv` своего поставщика из `checks.eval.providers`. Отдельный поставщик со своим адресом по умолчанию в сети проверок не работает.
3. Если eval снова даёт `stand_broken`, смотреть заметку отчёта и строки `[прокси eval]` в журнале врача (`docker compose -f deploy/compose.remontnik.yml logs doctor`).

## 0.1.8

Повтор случаев, закончившихся без излечения.

- **Случай, закончившийся без излечения, можно лечить заново.** Раньше `case <id> retry` отвечал `409 case_finished` на `report_only`, `no_cause_found`, `stand_broken`, `needs_human` и `not_helped`. Новый случай по тому же сбою тоже не открывался: повтор клеился к старому. Так случай, кончившийся «только отчётом» из-за поломки самого набора (в верстаке не было pnpm), оставался без лечения навсегда. Теперь команда начинает новую попытку: своя копия и ветка `-rN`, потолок случая `diagnoseUsdPerCase` заново. Дневные потолки, пределы автовыкаток и пометка «нужен человек» после отката прежние. `case_finished` — только для закрытых случаев (`healed`, `healed_by_paseo`, `rolled_back`).
- **Сам врач такой случай второй раз не лечит.** Повторы сбоя по-прежнему клеятся к открытому случаю: круга «сбой → отчёт → тот же сбой → снова лечить» без человека нет.
- **Отчёт говорит, как повторить.** Отчёты итогов без излечения (кроме «правка готова») кончаются строкой `Лечить заново: remontnik-doctor case <номер> retry` — и в Telegram, и в ленте для Paseo.
- **Где повтор может навредить, нужен `--force`.** Правка уже готова в ветке — отказ `409 fix_ready` с веткой: новая попытка лечила бы на новой ветке. После выкатки нужен человек (откат не удался, выкатка брошена, человек выкатил своё) — `409 deploy_needs_human`: сначала проверить, какая версия работает. Отчёт такого случая пишет команду сразу с `--force`. В обоих отказах врач пишет, что сделать. С `--force` повтор идёт, ответ называет ветку прошлой попытки (`previousBranch`), она остаётся.
- **Второго агента Paseo на случай нет.** Номер задачи у моста теперь хранится в случае, а не в памяти задачи. Если передача упала после письма агенту, новая попытка шлёт тот же номер, и мост его узнаёт. Передача, упавшая у врача прежней версии, номера не оставила: на неё отказ `409 handoff_unconfirmed`, пока владелец не проверит у моста и не повторит с `--force`.
- **Команда повтора не теряется в длинном отчёте.** Полный текст обрезается так же, как короткий: команда остаётся в конце целиком.
- **Повтор задачи, остановленной, пока случай у агента Paseo**, (`handoff_check`, `handed_off`, `paseo_working`, `reclaimed`) больше не получает ложный `case_finished`: остановленная задача продолжается, живая — `already_running`.

### Как обновить приложение

Все пакеты набора — `0.1.8`; менялся только врач, `watch` и `core` поднимать не обязательно, но версии набора держим одинаковыми.

1. Обновить врача: на сервере перевести клон Ремонтника на метку новой версии и пересобрать (`docker compose -f deploy/compose.remontnik.yml up -d --build`). Настройку приложения менять не нужно.
2. Найти номера случаев, которые кончились без излечения и ещё не вылечены: последний отчёт случая — `cause_found`, `no_cause_found`, `stand_broken`, `needs_human` или `not_helped` (лента отчётов или Telegram).
3. Если причина неудачи ушла (например, случай кончился «только отчётом» из-за pnpm в верстаке до 0.1.7), поставить случай в работу снова:

   ```bash
   docker compose -f deploy/compose.remontnik.yml exec doctor remontnik-doctor case <номер> retry --by owner
   ```

   Ответ `{"caseId":<номер>,"retried":"restarted","attempt":2}` — новая попытка началась. `409 already_running` — лечение уже идёт, `409 case_finished` — случай закрыт. `409 fix_ready`, `deploy_needs_human` или `handoff_unconfirmed` — врач пишет следующей строкой, что сделать. После этого та же команда с `--force`:

   ```bash
   docker compose -f deploy/compose.remontnik.yml exec doctor remontnik-doctor case <номер> retry --force --by owner
   ```

   Случаи, законченные до обновления, итог попытки не помнят. Отказа `fix_ready` и `deploy_needs_human` на них не будет. Если последний отчёт случая — «правка готова» или «нужен человек» после выкатки, сначала разберитесь с ним сами.

## 0.1.7

pnpm-приложения в верстаке врача и большие пакеты в зеркале реестра.

- **pnpm и yarn в образе без них.** В `node:22` pnpm нет, и установка pnpm-приложения падала с «pnpm: not found». Теперь врач сам кладёт в верстак заглушки `pnpm`, `pnpx` и `yarn` → `corepack <имя>`, если своих в образе нет, а corepack есть. `corepack enable` не нужен: корень контейнера только для чтения. Версия — из `packageManager` приложения. Её скачивает corepack через зеркало врача и сверяет подпись. Хранит её в HOME копии, поэтому команды проверок без сети её тоже видят. Своя программа образа важнее заглушки.
- **Зеркало реестра отдаёт одну версию пакета** (`/pnpm/10.33.2`, `/@scope/name/1.0.0`): так corepack узнаёт адрес архива pnpm и yarn. Раньше такой путь получал 400.
- **Предел метаданных пакета в зеркале — 256 МБ вместо 64.** Полные метаданные `@prisma/client` уже 68,5 МБ. pnpm 10 просит полный документ для необязательных зависимостей и в `pnpm view`. Ответ, как и раньше, идёт потоком и в памяти врача не копится. Защита от сжатых бомб, сроки и число одновременных ответов прежние.
- **check-config проверяет pnpm и yarn в образе верстака.** Проверка срабатывает, когда pnpm, pnpx или yarn зовёт одна из команд `workbench.install`, `checks.test` или `checks.typecheck`. Одного поля `packageManager` для неё мало: команды npm работают и без corepack. Проверка запускает образ так же, как верстак: тот же пользователь, те же пределы, без сети, корень только для чтения. Нет ни программы, ни corepack — ошибка. В образе нет sh — ошибка: врач запускает команды через `sh -c`. В `packageManager` другой менеджер (команды зовут pnpm, а там `npm@…`) — ошибка: corepack откажется. package.json не разбирается — ошибка. Есть только corepack, а `packageManager` нет — предупреждение. Образа нет на сервере или он не запустился по другой причине — предупреждение.
- **corepack не правит package.json копии.** Врач передаёт верстаку `COREPACK_ENABLE_AUTO_PIN=0`, и corepack не дописывает `packageManager` сам: в правке модели не появится лишняя строка.

### Как обновить приложение

Все пакеты набора — `0.1.7`; менялся только врач, `watch` и `core` поднимать не обязательно, но версии набора держим одинаковыми.

1. Обновить врача: на сервере перевести клон Ремонтника на метку новой версии и пересобрать (`docker compose -f deploy/compose.remontnik.yml up -d --build`).
2. pnpm-приложению на `node:22`: в `remontnik.config` оставить или вернуть `workbench: { image: 'node:22', install: 'pnpm install --frozen-lockfile' }`, а проверки писать как обычно (`pnpm test`). Ни `corepack enable`, ни `corepack pnpm` в командах не нужно.
3. В `package.json` приложения должно быть поле `"packageManager": "pnpm@<версия файла-замка>"`.
4. Проверить внутри контейнера врача: `remontnik-doctor check-config` — в разделе «верстак» «pnpm в верстаке — через corepack».

## 0.1.6

Своё git-хранилище на сервере вместо GitHub.

- **Своё хранилище на сервере вместо GitHub.** origin врача может быть bare-репозиторием на том же сервере под пользователем git с git-shell. Врач ходит по SSH своим ключом: `REMONTNIK_GIT_SSH_KEY` (текст ключа, с `\n` или base64) и обязательная с ним `REMONTNIK_GIT_KNOWN_HOSTS`. Токен не нужен. Ключ живёт только в окружении врача и во временной папке контейнера (права `0600`). Хранилище держат `receive.denyNonFastForwards`, `receive.denyDeletes` и хук `deploy/git-update-hook`: метки `remontnik/**` не двигаются и не удаляются, а ключ врача пишет только в основную ветку и `remontnik/**`. У каждого ключа в `authorized_keys` — `restrict` и принудительная команда `deploy/git-shell-remontnik-git` с путями его хранилищ: ключ ходит только в них и только к git, без оболочки, scp и sftp. Хук и config принадлежат root. Рецепт — `docs/security.md`, «Своё хранилище на сервере».
- **check-config для своего хранилища.** Для origin по SSH при заданном `REMONTNIK_GIT_SSH_KEY` вместо правил GitHub проверяет по SSH ключ и ключ сервера, настройки хранилища, хук, роль ключа врача, его привязку к хранилищу (проба в соседний путь должна получить отказ) и что пользователь git не пишет в config и хуки. Пробы ничего не записывают. Что хук и config принадлежат root, по SSH не проверить: всегда предупреждение с командой для root. С GitHub всё как раньше; origin по SSH без ключа врача — чужой хостинг, как раньше предупреждение «защита не проверена».
- **Образ и compose врача.** В образе есть `openssh-client`, у контейнера врача — `extra_hosts: host.docker.internal:host-gateway`: так он доходит до SSH сервера.

### Как обновить приложение

Все пакеты набора — `0.1.6`; в 0.1.6 менялся только врач, приложению поднимать `watch` и `core` не обязательно, но версии набора держим одинаковыми.

С GitHub:

1. На сервере перевести клон Ремонтника на метку новой версии и пересобрать врача (`docker compose -f deploy/compose.remontnik.yml up -d --build`). Настройку и окружение не менять.

Чтобы перейти на своё хранилище:

1. Обновить врача, как выше.
2. root на сервере делает хранилище, пользователя git и ключи по рецепту `docs/security.md`, «Своё хранилище на сервере»: хук и принудительная команда — из `deploy/` новой версии.
3. Человек отправляет в хранилище код со своего компьютера: `git push` своим ключом.
4. Закрытый ключ врача — в окружение врача `REMONTNIK_GIT_SSH_KEY` через `secret-handoff`, строка ключа сервера — в `REMONTNIK_GIT_KNOWN_HOSTS`. `REMONTNIK_GIT_TOKEN` убрать.
5. `REMONTNIK_APP_DIR` заменить клоном хранилища (`git clone --no-local`, origin `ssh://git@host.docker.internal/<путь>.git`, владелец `10001:10001`). `REMONTNIK_UID` оставить `10001`. Межсетевой экран сервера должен пускать SSH из подсетей Docker.
6. Перезапустить врача и проверить внутри его контейнера: `remontnik-doctor check-config` — ошибок нет, одно предупреждение про владельца хука; выполнить его команду от root.

## 0.1.5

Исправления сторожа по боевому приложению.

- **Очередь сторожа после перезапуска процесса в том же контейнере.** Раньше Docker перезапускал упавший процесс, тот снова получал номер 1, и сторож принимал замок прошлой жизни за живой: писал «уже открыта другим живым экземпляром» и заводил новый файл `outbox-<имя>.1-<метка>.jsonl` на каждый перезапуск. Теперь в замке записано и время запуска процесса (`/proc` на Linux, `ps` на остальных системах). Замок с нашим номером, но от другого запуска — от прошлой жизни: процесс снова пишет в основной файл `outbox-<имя>.jsonl`. Так же после пересоздания контейнера с тем же томом. Два живых процесса с одним `processName` на одной машине и второе открытие очереди в том же процессе по-прежнему пишут в разные файлы. Реплики в разных контейнерах на общем томе должны иметь разные `processName`, как и раньше.
- **`watch.wrapModelCatalog` и поставщики Agent Chat SDK.** Обёртка падала с `'get' on proxy: property 'connect' is a read-only and non-configurable data property…`: SDK задаёт `connect` у поставщика неизменяемым свойством. Теперь обёртка работает с неизменяемыми и замороженными каталогами, поставщиками и моделями, включая `doGenerate` и `doStream`. Для приложения каталог ведёт себя как раньше: те же поля, `connect` по-прежнему неперечисляемый. Поставщик, которого вернул `connect()` обёрнутого поставщика (и `extendCatalog` с `connectProviders`), тоже под присмотром: ошибки его моделей ловятся. Каталог, обёрнутый дважды, о сбое сообщает один раз.

### Как обновить приложение

1. Поднять `@ykurilov/remontnik-watch` и `@ykurilov/remontnik-core` до `0.1.5` точными версиями, пересобрать и перезапустить приложение. Клон Ремонтника для врача — на метку `v0.1.5`, пересобрать врача с теми же `-f`, что раньше (в 0.1.5 врач не менялся, но версии набора держим одинаковыми).
2. Уже накопленные файлы `outbox-<имя>.<pid>-<метка>.jsonl` и их замки трогать не нужно. При первом запуске новой версии процесс снова становится хозяином основного файла, переносит из этих файлов недоставленные случаи в основной файл и удаляет их.

## 0.1.4

Заголовки к поставщику модели в eval.

- **`upstreamHeaders` у поставщика eval.** У поставщика `checks.eval.providers[]` есть необязательное поле `upstreamHeaders`: список `{ name, valueEnv }`. Нужно, когда сервер приложения достаёт до поставщика только через свой обратный прокси, а тому нужен ещё один секрет (например, токен прокси). `valueEnv` — переменная в окружении врача, как `keyEnv`. Значение ставит только прокси врача: одноимённый заголовок от eval не проходит, в eval, отчёты и журналы значение не попадает. Нельзя задать заголовки прокси (`authorization`, `x-api-key`, `api-key`, `proxy-*`, `host`, `content-length`, `content-type`, `cookie`, `forwarded`, `x-forwarded-*`, `x-real-ip`, `accept-encoding`, заголовки соединения). Нет переменной у врача — ошибка `check-config`, eval не запускается. Без поля всё как раньше.

### Как обновить приложение

1. Поднять `@ykurilov/remontnik-watch` и `@ykurilov/remontnik-core` до `0.1.4` точными версиями. На сервере перевести клон Ремонтника на метку `v0.1.4` и пересобрать врача (`docker compose -f deploy/compose.remontnik.yml up -d --build`, с добавками — с теми же `-f`).
2. Если поставщику eval нужен свой заголовок — в `remontnik.config.ts` у поставщика добавить `upstreamHeaders: [{ name: '<имя заголовка>', valueEnv: '<ИМЯ_ПЕРЕМЕННОЙ>' }]`, значение положить в окружение врача под этим именем через `secret-handoff` и перезапустить врача. Не нужен — ничего не менять.
3. Проверить внутри контейнера врача: `remontnik-doctor check-config` — ошибок нет.

## 0.1.3

Приложение в сети сервера, вход через сервис авторизации, правила по умолчанию.

- **Приложение в сети сервера (`network_mode: host`).** Такое приложение не подключается к сети Docker. Для него есть добавка `deploy/compose.remontnik.host-app.yml`. Сеть приёма создаёт сам Ремонтник, приём опубликован только на `127.0.0.1` сервера (`REMONTNIK_HOST_PORT`, по умолчанию 7800), у сторожа `REMONTNIK_DOCTOR_URL=http://127.0.0.1:<порт>`. От браузера врача, сетей случая и других машин приём по-прежнему закрыт. Нужен Docker 28 или новее. `check-config` проверяет, что порт опубликован только на `127.0.0.1` и ведёт в сеть приёма (`gw_priority`).
- **`compose.remontnik.yml` читается в Docker Compose v5.** Раньше строка `aliases: [${REMONTNIK_DOCTOR_ALIAS:-…}]` давала ошибку разбора «did not find expected ','». Теперь имя в кавычках.
- **`origin` у `allowedMutations`.** Необязательное поле: точный сайт из `allowedOrigins`, правило действует только на нём. Нужно для входа через отдельный сервис авторизации. Без поля всё как раньше. `origin` вне `allowedOrigins` отклоняют служба браузера при старте и `check-config`.
- **Правила по умолчанию в `docs/getting-started.md`.** Копия кода у врача — чистый клон основной ветки. Ручная выкатка — только из закоммиченного состояния с текущей `origin/<основная ветка>`, с примером проверки на `git`. Ключи моделей Ремонтника — свои, с месячным лимитом у поставщика (по умолчанию 10 $ на ключ). Бот тревог — тот же бот, что у приложения. Рецепт «вход через сервис авторизации» — шаг 12 и `docs/security.md`.

## 0.1.0

Первый выпуск. Обновлять нечего: приложение подключается впервые.

### Что умеет набор

- **Сторож** (`@ykurilov/remontnik-watch`) живёт внутри приложения. Ловит падения, ошибки модели и инструментов, при желании — плохие ответы бота. Каждый сбой — одно сообщение в Telegram и одна запись случая; повтор увеличивает счётчик.
- **Врач** (`@ykurilov/remontnik-doctor`) работает отдельным контейнером на сервере приложения. Находит причину, правит код в отдельной ветке, проверяет тестами и eval. Выкатывает сам только при зелёных проверках, потом следит за приложением и откатывает, если стало хуже.
- **Границы.** Врач не трогает запретные зоны (схема базы, деньги, доступы) и существующие тесты. Есть потолки по деньгам и числу попыток; после них врач пишет «нужен человек». Упал сам врач — продолжит с места.
- **Браузер врача** (`@ykurilov/remontnik-browser`) — по желанию: повторить ошибку глазами пользователя.
  Пароль модель не видит. С первого вписанного пароля и до конца сеанса профиля браузер ходит только на адреса из `allowedOrigins`. Картинки, шрифты и CDN с других сайтов открывает поле `extraOrigins` (только подресурсы). Политику проверяет `remontnik-browser check-policy`, у врача — `check-config`.
- **Режим «сначала Paseo»** (`@ykurilov/remontnik-paseo-bridge`) — по желанию: случай сперва получает агент проекта, врач берёт его сам, если агент недоступен или замолчал.
- Код приложения Ремонтник не правит: подключение делает агент приложения в его репозитории и на его сервере.

### Как подключить

Полная пошаговая инструкция — [docs/getting-started.md](./docs/getting-started.md). Каждый шаг там кончается проверкой. Коротко:

1. Спросить владельца только то, чего нет в коде: репозиторий и основная ветка, сервер и ручная выкатка, чат и бот Telegram, нужны ли браузер и режим «сначала Paseo».
2. Поставить `@ykurilov/remontnik-watch` и `@ykurilov/remontnik-core` точными версиями. Врача в приложение не ставить.
3. Подключить сторожа в каждый процесс приложения (`createWatch`).
4. Написать `remontnik.config.ts` в корне: запретные зоны, где врач может править, команды проверки.
5. Дать команды выкатки `build`, `promote`, `confirm`, `rollback`, `current`, `health`. `promote` выходит, только когда кандидат уже отвечает. Адреса команды берут из своих файлов на сервере: переменные с `URL` в имени врач им не передаёт. Проверить вручную: `build` → `promote` → `rollback`.
6. По желанию — eval и службы для тестов.
7. Задать окружение сервера; секреты — только через `secret-handoff`.
8. Запустить врача контейнером из `deploy/compose.remontnik.yml`.
9. Проверить: `remontnik-doctor check-config` пишет «ошибок нет».
10. Включить правила GitHub и стоп-кран; по желанию — браузер врача и режим «сначала Paseo».
11. Прогнать тестовый сбой: он доходит до врача и в Telegram, ручной `rollback` возвращает прежнюю версию.
