# Исследование: Ремонтник Pi

Решения по технике для [plan.md](./plan.md). Формат: решение → почему → что отвергли.

## R1. Каркас врача — `@earendil-works/pi-durable` 1.4.0, точно

- **Решение**: врач строится на pi-durable 1.4.0 (вышел 21.10.2026, MIT, Node ≥ 22.19). В `package.json` версии `pi-durable`, `pi-ai`, `chord` пишутся без `^` и `~`. Автообновлений (Dependabot, Renovate) в репозитории нет; скрипт `scripts/check-pins.mjs` в `pnpm verify` падает, если у этих пакетов появился диапазон.
- **Почему**: README пакета — «Experimental. The API changes without notice». В 1.4.0 ломающие изменения и необратимая миграция SQLite на схему 2; в Unreleased снова ломающие. Обновление — отдельная задача с чтением CHANGELOG и прогоном тестов падений.
- **Что берём из pi-durable**:
  - `Harness.open(storage, …)` + `harness.resume()` — продолжение после падения.
  - Хранилище `/storage/sqlite/node` (один файл, WAL). JSONL не берём: держит всю историю в памяти.
  - `defineTask` с фазами — конвейер лечения; чекпойнт на каждом шаге. Фаза после рестарта идёт заново с начала → внешние действия по схеме «намерение → действие → итог» с проверкой реального состояния.
  - Переписка с моделью на каждый случай; инструменты `CodingTools` (read, write, edit, bash) через своё окружение выполнения (R4).
  - `runtime.sleepUntil` — окно наблюдения после выкатки переживает рестарт.
  - `onReport` — тревога при `task_parked` (5 падений подряд без прогресса).
  - Хуки `beforeTool` (принудительный тайм-аут bash, запрет путей), `beforeRequest` (потолок расходов), `afterResponse` (учёт расходов).
- **Чего в pi-durable нет — пишем сами**: запасной поставщик модели (R2), внешние сигналы (используем `conversation.submit({type:"write"})` и документы), блокировка между процессами (один процесс врача на приложение, перезапуск — политикой Docker `restart: unless-stopped`).
- **Риски и ответ на них**:
  - Bash без тайм-аута по умолчанию → `beforeTool` всегда ставит тайм-аут (по умолчанию 10 минут, настраивается).
  - Дочерние процессы `detached` могут остаться сиротами → все команды модели идут через `docker exec` в контейнер-верстак; при старте врач перезапускает верстак незавершённого случая.
  - Ошибка хранилища закрывает Harness → `harness.closed` с причиной `failed` → процесс выходит с ненулевым кодом, Docker перезапускает, Telegram получает тревогу.
  - Последняя секунда потока теряется при падении → учёт расходов с запасом 10%.
- **Отвергли**: свой конвейер на SQLite без pi-durable (решение Юрия — pi-durable); Temporal и подобное (тяжело, отдельный сервер, ученикам сложно).

## R2. Модель: DeepSeek 4.1 Flash, запасной путь OpenRouter

- **Решение**: один модуль `model-route` в `remontnik-core` описывает путь: основной — DeepSeek API, модель DeepSeek 4.1 Flash; запасной — OpenRouter `deepseek/deepseek-v4.1-flash-1017`. Переход на запасной — при 429, 5xx, сетевой ошибке и тайм-ауте соединения; при 4xx (кроме 429) — сразу ошибка. Возврат на основной — после паузы (по умолчанию 10 минут).
  - Сторож (внутри приложения) ходит через лёгкий клиент на `fetch` по OpenAI-совместимому протоколу — без тяжёлых зависимостей в приложении.
  - Врач ходит через `pi-ai`: обёртка-поставщик над `deepseekProvider()` и `openrouter`, которая реализует тот же порядок переходов.
- **Почему**: решение Юрия. В pi-ai готового запасного пути нет (R1). Порядок переходов совпадает с тем, что уже работает в Генераторе лидмагнитов (`withDirectModel`).
- **Имя модели**: `deepseek-flash` — псевдоним поставщика (в API DeepSeek за ним сейчас DeepSeek-V4.1-Flash); версия за ним может смениться без нашего ведома.
- **Уровень рассуждения при чтении разговоров**: `low` (по умолчанию, настраивается `review.reasoningEffort`). Живой прогон на выдуманном наборе (18 плохих, 24 хороших разговора, рубрика с местами): `low` — найдено 18/18, ложных 0/24, 6295 токенов выхода; `high` — найдено 17/18, ложных 0/24, 6036 токенов выхода. Выше уровень не дал ни точности, ни экономии, а читать приходится много разговоров подряд, поэтому берём `low`. Набор небольшой: при смене рубрики или модели прогон повторить (`REMONTNIK_LIVE_EFFORT`).
- **Адреса и прокси**: базовые адреса обоих путей и заголовок прокси (`X-Proxy-Token`) — только из окружения. Для серверов в России — через прокси, по инструкции подключения.

## R3. Кэш модели

- **Решение**:
  - Системный промпт врача собирается из неизменных секций в постоянном порядке: роль и правила → описание приложения из настройки → карта репозитория (меняется только с новым коммитом основы). Текущее время, номер случая и прочее меняющееся в системный промпт не попадает.
  - Данные случая — первым сообщением переписки, дальше — работа инструментами. Одна переписка на случай: продолжение после падения переиспользует кэш (pi-durable хранит `sessionId`, для OpenRouter уходит `x-session-id`).
  - Набор инструментов на переписку постоянный: смена набора ломает кэш. Инструменты браузера, когда браузер недоступен, не убираются, а отвечают «браузер недоступен».
  - Сторож: рубрика оценки разговора и описание бота — неизменный префикс, сам разговор — в конце. Разговоры оцениваются по одному, тем же префиксом.
- **Почему**: DeepSeek кэширует по совпадающему началу запроса автоматически, кэшированные токены в разы дешевле.

## R4. Где работает модель врача: контейнер-верстак

- **Решение**: на каждый случай — рабочая копия (`git worktree`) репозитория приложения и контейнер-верстак из образа разработки приложения (Node, pnpm). Модель выполняет `read/write/edit/bash` только внутри верстака через своё окружение выполнения (`ContainerExecutionEnv`: `docker exec` с тайм-аутом). В верстаке:
  - только рабочая копия; закрытые папки (`closedPaths`, например отложенные сценарии eval) физически убраны из копии (sparse checkout);
  - нет секретов боевого приложения, нет сокета Docker, нет доступа к базе приложения;
  - сеть есть (нужна установка пакетов), но без доступа к внутренней сети приложения.
- **Почему**: модель не должна ни видеть секреты, ни выкатывать. Выкатку, откат, проверки и git-операции с удалённым репозиторием делает обычный код врача (оркестратор), а не модель.
- **Отвергли**: `NodeExecutionEnv` прямо в процессе врача (модель видела бы окружение врача с ключами и сокет Docker).

## R5. Проверки: тесты и eval

- **Решение**:
  - Тесты и eval запускает оркестратор в отдельном проверочном контейнере на закоммиченной правке, командами из настройки приложения. Модель может гонять юнит-тесты в верстаке во время поиска, но итог для решения о выкатке — только прогон оркестратора.
  - Затронутые сценарии eval выбираются кодом по карте «пути → сценарии» из настройки (`evalScope`), не моделью. Правка вне карты → eval не нужен. Потолок числа сценариев и денег на прогон.
  - «Не хуже» = по каждому затронутому сценарию число успешных повторов не меньше, чем у основы. Итог основы кэшируется по паре (коммит, сценарий), чтобы не гонять её каждый раз.
  - Нестабильность: упавшие тесты повторяются один раз; разный итог = красный.
  - Итоги «стенд сломан» и «персонаж вышел из роли» — не «правка плохая», но и не зелёный: выкатки нет.
  - Коллегия судей из агентов Paseo на сервере недоступна и в решение не входит.
  - Для eval на сервере — отдельные ключи моделей с маленьким лимитом расходов и отдельная база для прогонов.
- **Почему**: решение о выкатке должно опираться на то, что модель не может подменить.

## R6. Решение о выкатке — чистая функция

- **Решение**: модуль `deploy-gate` — чистая функция от фактов (итоги проверок, список изменённых файлов, дифф, стоп-кран, счётчики попыток и расходов) к решению «выкатить / только отчёт» с причинами. Условия «только отчёт»:
  1. Тесты не зелёные или нестабильны; eval хуже основы, «стенд сломан» или не запускался, хотя должен.
  2. Изменён файл запретной зоны (R7).
  3. Изменён или удалён существующий тест, сценарий eval, рубрика или судья (добавлять новые можно).
  4. Подозрительные изменения: новые обращения к переменным окружения, новые внешние адреса, запуск процессов, `eval`/динамический код, работа с файлами вне проекта.
  5. Дифф больше порога (по умолчанию 300 строк или 15 файлов).
  6. Стоп-кран включён; лимит попыток по отпечатку или в сутки исчерпан; отпечаток помечен «нужен человек» после отката; потолок расходов достигнут.
  7. Основа устарела и перенос правки дал конфликт.
- **Почему**: тестируется полностью без моделей и сети; модель не может уговорить код.
- Пункты 3–5 — мои защитные значения по умолчанию в рамках решения Юрия «доступы и ключи — никогда»: код, который читает окружение, касается ключей. Настраиваются в настройке приложения.
- Нет данных — нет выкатки: факты неполные или невозможные (не число, неизвестное слово, пустая правка) дают `report_only` с причиной `facts_invalid`.
- **Оговорка**: осмотр диффа и запретные зоны ищут признаки шаблонами по тексту. Они защищают от ошибок и самоуверенности модели, а не от намеренной подмены: адрес, собранный из кусочков, или `require` по вычисленному имени шаблон не поймает. Против такого стоят права git, метки прежней версии и откат (R8, R9).

## R7. Запретные зоны

- **Решение**: всегда запрещены (нельзя выключить настройкой):
  - схема базы и миграции — маски из настройки (`forbidden.schema`) плюс признаки в диффе (`CREATE TABLE`, `ALTER TABLE`, `DROP` в SQL-файлах);
  - деньги и оплата — маски из настройки (`forbidden.money`);
  - доступы и ключи — маски из настройки (`forbidden.access`), плюс всегда `.env*`, `*.env`, `*.pem`, `*.key`, файлы с `secret`/`credential` в имени;
  - код Agent Chat SDK — всё в `node_modules/@ykurilov/agent-chat-*`, патчи пакетов (`patches/`, `pnpm.patchedDependencies`) для `@ykurilov/agent-chat-*`;
  - сам Ремонтник: файл настройки `remontnik.config.*`, зависимости `@ykurilov/remontnik-*`.
- По умолчанию запрещены, но настраиваются (мои значения): зависимости и файл-замок, `Dockerfile`, файлы выкатки, CI.
- Настройка приложения читается врачом **только из основной ветки**, никогда из ветки правки.
- Маски конкретного приложения задаёт его агент при подключении. Для Генератора лидмагнитов они собраны в частном файле вне git (`.private/lead-magnet-integration.md`): в открытый репозиторий устройство закрытого приложения не попадает.

## R8. Git и права

- **Решение**:
  - Ветки врача — `remontnik/<номер-случая>-<коротко>`; метки — `remontnik/pre-deploy/<дата>-<номер>` на прежней рабочей версии.
  - Модуль `git-guard` — единственный путь к git с удалённым репозиторием. Белый список операций: fetch, создать свою ветку, push своей ветки без `--force`, создать метку `remontnik/*`. Слияние в основную ветку — только обычный push, без `--force`, и только если включено настройкой (`repo.mainline: "merge"`, по умолчанию — решение Юрия по вопросу 3).
  - На GitHub — правила хранилища (ruleset): основная ветка — запрет принудительной записи и удаления; метки `remontnik/**` — запрет изменения и удаления. Шаблон правил — `deploy/github-ruleset.json`, применяет установщик через `gh api`.
  - Ключ доступа врача — отдельный, только к репозиторию приложения, хранится в окружении сервера.
- **Почему**: решение Юрия «свои ветки и метки, без переписывания истории» держится правами GitHub, а код врача — второй замок.
- **Оговорка**: проверки кода врача (осмотр диффа, запретные зоны) рассчитаны на ошибки модели. Намеренную подмену останавливают именно права на стороне GitHub и ключ врача, поэтому они обязательны.

## R9. Выкатка, наблюдение, откат

- **Решение**: врач не знает, как устроена выкатка конкретного приложения. Приложение даёт команды (контракт [contracts/deploy-commands.md](./contracts/deploy-commands.md)): `build`, `promote`, `confirm`, `rollback`, `current`, `health`. Каждый шаг — «намерение → команда → проверка `current`/`health`».
  - Прежняя сборка: перед `promote` врач требует, чтобы `current` вернул версию, у которой есть сохранённая сборка (например, прежний образ и прежний файл запуска). Откат — `rollback` без git.
  - Наблюдение: окно 30 минут по умолчанию. Откат, если: проверка здоровья не прошла 3 раза подряд; или частота ошибок от сторожа выше уровня до выкатки в заданное число раз и выше минимального порога; или появились новые отпечатки сбоев, не виденные за 7 дней, сверх порога. Повтор того же отпечатка без ухудшения — «не помогло», без отката, попытка засчитана.
  - Замок выкатки: файл-замок на сервере, общий с ручной выкаткой приложения. Ручная выкатка во время наблюдения → `current` сменился → врач прекращает наблюдение и не откатывает чужое.
  - Если нет ответа от `current` после падения врача посреди выкатки — врач откатывает и сообщает.
- **Почему**: у приложений Юрия выкатка разная; общая часть — правила, а не команды.

## R10. Сторож внутри приложения

- **Решение**: пакет `@ykurilov/remontnik-watch` без тяжёлых зависимостей (только `remontnik-core`).
  - Ловит: `process.on('uncaughtException' | 'unhandledRejection')`; ошибки моделей и инструментов через обёртку каталога моделей и хуки Agent Chat SDK (подпуть `/agent-chat`: `logError`, `afterTurn`, `turnNotStarted`); явный `watch.capture(error, where)`.
  - Очередь случаев: файл с дозаписью (JSONL) на процесс в папке из окружения; запись подтверждения после ответа врача. Переживает перезапуск. Веб и фоновый работник пишут каждый в свой файл.
  - Telegram сразу, своими силами, через бота тревог приложения (токен из окружения, чат — значением или функцией приложения: чат может храниться в базе приложения).
  - Склейка: отпечаток = вид + место (первая строка следа внутри кода приложения) + текст ошибки без чисел, адресов и идентификаторов. Повторное сообщение по случаю — не чаще раза в час и только при росте счётчика.
  - Свои ошибки глушит и пишет в журнал процесса одной строкой с пометкой `[remontnik]`.
- **Почему**: приложение не должно платить за сторожа ни зависимостями, ни скоростью.

## R11. Чтение законченных разговоров

- **Решение**: приложение вызывает `watch.conversationFinished({ id, messages, meta })` в месте, где разговор закрывается . Сторож ставит разговор в очередь и в фоне, по одному, оценивает моделью по рубрике: выдумка, грубость, выход из роли, пропущенный вопрос, обрыв, противоречие инструкции бота. Ответ — строгий JSON: список отметок с номером сообщения, видом, выдержкой, объяснением, уверенностью. Отметки ниже порога уверенности не становятся случаями.
  - Личные данные маскируются до отправки в модель.
  - Дневной бюджет; сверх бюджета — разговоры ждут, сводка сообщает «отложено N».
  - Одинаковые отметки склеиваются отпечатком (вид + место в инструкции бота).
  - Качество проверяется на выдуманном размеченном наборе разговоров (SC-009), живой группой тестов.
- **Почему**: решение Юрия — сторож в приложении; разговоры уже там.

## R12. Браузер Ремонтника

- **Решение**: свой пакет `@ykurilov/remontnik-browser` — отдельная служба в своём контейнере на том же сервере. Основа — `playwright-core` (Apache-2.0) с Chromium (BSD). Команды и правила — по образцу SmartRemoteBrowser; его код не копируем (у проекта нет лицензии, он тянет закрытые зависимости, и он нам велик). Прокси выключен по умолчанию, включается настройкой профиля.
  - Команды (HTTP с ключом врача и консольная `remontnik-browser`): `open`, `url`, `back`, `read` (снимок страницы с номерами элементов), `click`, `type`, `key`, `scroll`, `shot`, `logins`, `fill-password`, `status`.
  - Снимок с номерами — доступность-снимок Playwright (`ariaSnapshot`); если в закреплённой версии нет номеров элементов — свой обход DOM с отметками `data-remontnik-ref`. Выбор фиксируется при реализации с тестом.
  - Профиль Ремонтника — постоянная папка браузера на томе службы; имя профиля и адреса — только настройкой.
- **Защита паролей (ответ на вопрос Юрия)**:
  1. Пароли — в зашифрованном файле (AES-256-GCM) на томе браузера; ключ шифрования — в окружении только контейнера браузера. У врача и верстака нет ни тома, ни ключа.
  2. Добавление входа — командой на сервере с чтением пароля из стандартного ввода (`logins add --password-stdin`); пароль не проходит через аргументы, журналы и модель. Агент на Маке передаёт его из `~/.codex/secrets/` по skill `secret-handoff`.
  3. `fill-password <вход> <элемент>` впечатывает сам браузер, только если элемент — поле пароля и адрес документа поля (с фреймом) совпадает с сайтом входа или его поддоменом.
  4. Модель не может выполнять свой код на странице: такой команды нет.
  5. Снимок страницы никогда не содержит значения полей пароля и полей, куда впечатан пароль, даже если страница сменила им тип на текст. Снимок экрана закрывает такие поля маской (`screenshot({ mask })`).
  6. Ответы и журналы службы проходят через фильтр, который вырезает значения всех сохранённых паролей, — последний замок.
  7. Тест SC-010 ищет пароль во всех выводах после входа, показа пароля кнопкой «глаз», смены типа поля и снимков.
  - **Остаток риска**: ключ шифрования лежит на том же сервере; полный доступ к серверу или побег модели из верстака открывают пароли. Юрий принял этот риск (вопрос 6) вместе с отдельной слабой учёткой (вопрос 5).
- **Опасные действия**: три замка.
  1. Модель обязана указать вид действия (`none` / `submit` / `send` / `pay` / `delete` / `publish`); `send`, `pay`, `delete`, `publish` отклоняются.
  2. Сетевой замок: браузер пропускает изменяющие запросы (не GET) к сайту приложения только по белому списку путей из настройки (`allowedMutations`, например вход и отправка сообщения боту в веб-чате); остальные блокируются. Это настоящая защита даже при неверно указанном виде действия.
  3. Переходы — только на сайты из `allowedOrigins`.
- **Капча и коды**: признаки на странице (рамки известных капч, поля `autocomplete="one-time-code"`, тексты про код подтверждения) → команда возвращает `needs_human`, врач сообщает.
- **Без браузера**: инструменты браузера у модели есть всегда, при недоступной службе отвечают «браузер недоступен»; отчёт помечается «без проверки в браузере».
- **Живой экран** (решение Юрия, вопрос 7):
  - Кадры — трансляция экрана Chromium через протокол отладки (`context.newCDPSession(page)`, `Page.startScreencast`, JPEG) по WebSocket на страницу службы; мышь, касания и клавиши — обратно через `Input.dispatchMouseEvent` / `dispatchKeyEvent` / `insertText`. Без X-сервера и VNC: работает с браузером без окна.
  - Доступ: отдельный адрес службы только на адресе частной сети (`REMONTNIK_BROWSER_LIVE_LISTEN`); вход по ключу владельца (`REMONTNIK_BROWSER_OWNER_TOKEN`, отдельный от ключа врача) → куки только для этого адреса. Без частной сети живой экран не включается (тот же принцип, что у моста Paseo: один путь, из интернета не видно).
  - Управление: кнопки «Взять управление» / «Вернуть». Пока управление у владельца, команды врача отвечают `refused_human_control`; связь владельца оборвалась — управление возвращается через 2 минуты. Замки сайтов и изменяющих запросов действуют и при ручном управлении: профиль принадлежит Ремонтнику.
  - Кадры идут только на страницу владельца: в ответы врачу, журналы и отчёты не попадают. Владелец — человек, ему видно всё, что видно на экране.
  - Отчёт `needs_human` от браузера (капча, код) несёт ссылку на живой экран; после «Вернуть» врач продолжает с того же шага.

## R13. Отчёты

- **Решение**:
  - Telegram: врач шлёт через того же бота тревог приложения; очередь с повторами (сохранена в хранилище врача, переживает рестарт). Длинный отчёт — коротко в сообщении; полный текст хранится у врача и выдаётся по номеру отчёта.
  - Paseo: врач хранит отчёты с курсором. Мост Paseo на компьютере владельца (R18) забирает новые по частной сети (`GET /v1/reports?after=<курсор>`), пересылает главному агенту приложения и подтверждает курсор. В каждом отчёте его номер — мост не шлёт номер дважды. Мост выключен — отчёты копятся и уходят после включения.
  - Стоп-кран: команда `remontnik-doctor deploys stop|resume` и HTTP-адрес с подписью — для кнопки «Остановить автовыкатку» под отчётами в Telegram; нажатие передаёт приложение (решение Юрия по вопросу 8).
- **Почему**: Telegram — всегда; Paseo — когда доступен, без пропусков.

## R14. Открытый репозиторий без секретов

- **Решение**:
  - `gitleaks` по дереву и истории в CI и перед выпуском.
  - Свой скрипт `scripts/check-public.mjs`: публичные IPv4, домены вне `example.com/.test/.invalid`, строки вида ключей. Частный запретный список (настоящие домены и адреса Юрия) лежит **вне репозитория** (`~/.config/remontnik/denylist.txt`) и подключается локально перед push и выпуском: сам список в открытый репозиторий попасть не может.
  - Примеры — `example.com`, выдуманные имена и данные.
- **Почему**: решение Юрия; список настоящих адресов в репозитории сам был бы утечкой.

## R15. Выпуск и обновление

- **Решение**: как у Agent Chat SDK — pnpm-монорепозиторий, changesets с группой `fixed` (все `@ykurilov/remontnik-*` одной версией), общий npm, `CHANGES.md` в корне со всеми шагами «Как обновить приложение», `RELEASING.md`. Пока `0.x`: minor — новая возможность или ломающее, patch — исправление. Скилл для агентов-установщиков (`remontnik`) — по образцу `agent-chat-sdk`, вне этого репозитория, создаётся после первого выпуска.
- **Лицензия**: MIT (решение Юрия по вопросу 1). Файл `LICENSE` в корне, поле `license` во всех пакетах.

## R16. Учебное приложение «Пациент»

- **Решение**: `apps/patient` — маленькое приложение на Node без внешних служб: несколько страниц (кабинет со входом, веб-чат с подставным ботом), тесты, подставной eval (сценарии с заранее известным итогом, без моделей), команды выкатки на папках (`releases/<версия>`, ссылка `current`, `previous`) вместо Docker. ## R18. Режим «сначала Paseo» и мост

- **Решение Юрия**: по желанию врач сначала отдаёт случай главному агенту приложения в Paseo; лечит сам, только если тот недоступен. Связь — напрямую по частной сети (Tailscale или похожая), одним путём.
- **Мост** — пакет `@ykurilov/remontnik-paseo-bridge`, плагин Paseo по образцу `agent-alerts`: серверная часть плагина работает внутри Paseo на компьютере владельца, держит свой HTTP-адрес только на адресе частной сети и пишет агенту через API плагина (`agents.ref(id).send`). Какому агенту отдавать случаи какого приложения — настройка моста на компьютере владельца (`~/.config/remontnik/paseo-bridge.json`), в репозиторий и на сервер идентификаторы агентов не попадают.
- **Передача** (фазы задачи лечения, с чекпойнтами):
  1. `handoff_check`: `GET <мост>/health?app=<имя>` с коротким тайм-аутом (3 с). Нет ответа, Paseo не работает или агента нет → врач лечит сам, отчёт с пометкой «Paseo недоступен».
  2. `handed_off`: `POST <мост>/v1/tasks` с подписью → мост пишет агенту задачу. Врач ждёт подтверждения `accepted` (агент вызывает команду моста) до `acceptTimeoutMs` (5 мин) через `runtime.sleepUntil`; модель врача не работает.
  3. `paseo_working`: ждёт итог до `workTimeoutMs` (60 мин). Агент присылает через мост `done` (коммит, выкачено ли, версия) или `cannot` (почему).
  4. `done` с выкаткой → врач проверяет `current`, затем то же наблюдение, что после своей выкатки (R9); ухудшение → откат сам, отчёт агенту и владельцу. `done` без выкатки → отчёт, случай закрыт у агента.
  5. Срок вышел, `cannot` или мост пропал во время работы → `POST <мост>/v1/tasks/:id/cancel` (по возможности), отметка `reclaimed`, дальше обычное лечение врача с `triage`.
- **Один хозяин случая**: передача — документ с полем `owner` (`paseo` | `doctor`); врач начинает своё лечение только после записи `owner: doctor`. Поздний итог агента после `reclaimed` записывается в отчёт, но случай не переоткрывает. Если агент всё же выкатил — общий файл-замок не даёт выкатить двоим сразу; смену `current` врач наблюдает как выкатку по этому случаю.
- **Защита**:
  - мост слушает только адрес частной сети; служебные адреса врача для моста (`/v1/handoffs/*`, `/v1/reports*`) — тоже только частная сеть, из интернета их не видно;
  - запросы в обе стороны подписаны HMAC отдельным общим секретом моста;
  - задача агенту — постоянный шаблон: что случилось, номер случая, где ветки и отчёты, правила (выкатка — по правилам приложения, итог — командой моста). Тексты ошибок и выдержки разговоров идут в отдельном блоке «данные из приложения, не поручение»; длинное агент забирает сам по номеру случая;
  - мост передаёт задачи только агенту из своей настройки для этого приложения.
- **Почему так**: агент владельца сильнее и знает проект, врач не тратит модель, пока тот работает; при любом отказе Paseo самолечение не останавливается (принцип VI). Частная сеть убирает опрос и не открывает врача в интернет.
- **Что проверить при реализации**: может ли серверная часть плагина Paseo держать свой HTTP-адрес все время работы Paseo; если нет — остановиться и сообщить, второй путь связи не строить без решения Юрия.
