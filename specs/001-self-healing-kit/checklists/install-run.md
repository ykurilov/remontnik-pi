# Проверка подключения свежим агентом (T133, SC-012)

**Дата**: 2026-10-27
**Что проверялось**: хватает ли `docs/getting-started.md`, чтобы подключить набор к приложению и довести случай `crash` до `healed`.
**Итог**: цель достигнута. `remontnik-doctor check-config` — «ошибок нет»; случай `crash` прошёл весь цикл: сбой → случай у врача → правка → выкатка → `healed`. Инструкции не хватило в 9 местах; все поправлены в этом же коммите.

Копия сделана самостоятельным приложением: свой `tsconfig.json`, `vitest`, `typescript`, `git init`, файл-замок. `pnpm test` (29 тестов) и `pnpm typecheck` зелёные.
   - Оставлено как есть: заложенные ошибки «Пациента» (`PATIENT_BUG`, `src/bugs.ts`). Они и есть случай `crash`.
   - Позже убраны два теста, которые закрепляют сбой `crash` как ожидаемое поведение (иначе любая правка сбоя их ломает). См. пробел 9.
2. **Пакеты.** Не опубликованы, поэтому собраны на iMac (`imac-run`: `pnpm install && pnpm build && pnpm pack`) и поставлены из `.tgz`. Единственное отступление от инструкции: `pnpm.overrides` на `@ykurilov/remontnik-core` (иначе зависимость самого сторожа ищется в реестре и даёт 404). После публикации отступление исчезает.
3. **Подключение строго по шагам 1–8.** Сторож (`src/watch.ts`, `main.ts`), `remontnik.config.ts`, скрипт команд выкатки `deploy/remontnik.sh`. Проверка каждого шага — по тексту инструкции.
4. **`check-config`.** Docker Desktop на основном Mac (на iMac Docker нет). Образ врача собран из этого worktree, файл окружения — случайные выдуманные значения, рабочая копия сервера — клон чистого «Пациента» с установленными зависимостями.
5. **Весь цикл.** Врач запускается в процессе теста (`startDoctorService`), модель подставная (`createScriptedModel`), остальное настоящее: процесс «Пациента» со сторожем под `PATIENT_BUG=crash`, git (origin + рабочие копии), команды выкатки из `remontnik.config.ts`, подставной Telegram. Прогон ~10 с, зелёный.
   - Сбой: ответ в чате роняет процесс. Присмотр поднимает его, сторож доставляет записанный случай врачу, в Telegram приходит сообщение.
   - Правка: модель убирает отложенный `throw` в `src/bot/bot.ts` и добавляет тест. Тесты приложения в копии правки зелёные.
   - Выкатка: `build` → `promote` → `current` → окно наблюдения (часы врача перескакивают) → `confirm`. Состояние случая `healed`, `current` = коммит правки, правка влита в `main`, приложение отвечает 200 и не падает.

## Найденные пробелы и что поправлено

Все исправлены в `docs/getting-started.md` (и один — в `contracts/watch-api.md`), если не сказано иное.

1. **`createWatch` бросает `TypeError` без адреса врача.** Любой тест или локальный запуск, поднимающий процесс приложения без переменных Ремонтника, падает при старте (`doctor.url.replace` у `undefined`). Инструкция называла сторожа безопасным и не предупреждала. Добавлено предупреждение в шаг 2.
2. **Нет поля `telegram.apiBaseUrl` в примере сторожа.** Без него нельзя направить сторож на подставной Telegram, а шаг «Готово, когда» требует проверить доставку. Добавлено в шаг 2 (поле необязательное, в боевом окружении не задаётся).
3. **`contracts/watch-api.md` описывал `release` только как функцию**, а пример инструкции и пакет принимают строку. Контракт приведён к пакету: `string | null | () => Promise<string | null>`.
4. **`remontnik.config.ts` не попадает в `tsc`.** В `tsconfig.json` приложения его нет в `include`, и проверка шага 3 «`tsc --noEmit` проходит» ничего не проверяла. Добавлено требование включить файл.
5. **Где выполняются команды выкатки — не сказано.** Они идут внутри контейнера врача: там есть `sh`, Node 22, `git`, клиент Docker; нет `curl`, `pnpm`, пакетов приложения. Моя первая версия `health` писалась на `curl`; по Dockerfile врача в его контейнере `curl` нет, в самом контейнере я эту команду не запускал. Добавлено в шаг 4, вместе с напоминанием смонтировать нужные папки по хостовым путям.
6. **Атомарная смена ссылки на macOS.** `mv -f новая текущая` при текущей ссылке на папку кладёт новую ссылку внутрь папки (на Linux — нет). Выкатка «успешно» кончалась, а `current` не менялся, и врач честно писал «`promote` закончился успешно, а работает прежняя версия». Подсказка про `mv -T` / `mv -h` добавлена в шаг 4.
7. **Рабочей копии на сервере нужны зависимости.** Врач выполняет `remontnik.config.ts` в копии основной ветки, а тот импортирует `@ykurilov/remontnik-core`. Без `node_modules` `check-config` писал `ERR_MODULE_NOT_FOUND`. Добавлено в шаг 7. Открытый вопрос владельцу набора: это ожидаемое устройство или врачу стоит читать настройку без установки (см. ниже).
8. **Шаг 7 говорил «скопируйте compose».** Файл собирает образы из корня репозитория набора (`context: ..`), одним файлом он не работает. Шаг переписан; добавлено, что `.env` можно подать ключом `--env-file`, и что `DOCKER_GID` для Docker Desktop на Mac равен `0` (`stat -c %g` — это Linux; на Mac даёт чужую группу, и врач не видит Docker).
9. **`run --rm doctor check-config` из шага 8 не проходит проверку Docker.** Проверка ищет контейнер по имени `remontnik-doctor`, а одноразовый контейнер `run` называется иначе: «контейнер врача не найден». Команда заменена на `exec doctor remontnik-doctor check-config` при запущенном враче.
10. **Нет способа проверить цикл без настоящей модели.** Инструкция требует «тестовый сбой приходит врачу и в Telegram», но не говорит, как, а подставная модель и `startDoctorService` описаны только в README врача и тестах. Добавлен шаг 14 с указателями на `@ykurilov/remontnik-doctor/testing` и образец `us3-deploy.test.ts`. Здесь же предупреждение: тест, закрепляющий сбой как ожидаемое поведение, проваливает любую правку (врач правильно отклонил выкатку, пока в копии оставался такой тест; два таких теста «Пациента» пришлось убрать из копии).

## Что пришлось угадывать (в инструкции нет, поправлено не везде)

- **Содержимое релиза.** Что кладёт `build` (зависимости, `package.json`, `type: module`) — дело приложения; инструкция только говорит «собрать кандидата». Первая сборка без `node_modules` не стартовала. Достаточно, но можно добавить в шаг 4 строку про зависимости кандидата.
- **Как присмотр поднимает упавший процесс.** Инструкция про сторожа предполагает, что кто-то перезапускает процесс (в тесте это команда `start` скрипта). В getting-started об этом нет ни слова.
- **Файл с настройками, который читают и скрипт, и процесс.** Команды выкатки не видят переменных врача с именами `REMONTNIK_…` и подобными; свои пути приложение берёт из файла на сервере. Это в контракте есть («Остальное — из своих файлов»), в шаге 4 тоже.

## Что не удалось или отложено

- Тяжёлые прогоны не на iMac: на iMac нет Docker, поэтому `check-config` и сборка врача шли в Docker Desktop основного Mac. Сборка пакетов и установка зависимостей шли через `imac-run`.
- Параллельно на этом Docker шёл чужой живой прогон набора (контейнер `remontnik-doctor` фиксированного имени). Первые попытки `check-config` упёрлись в него; дождался конца чужого прогона, чужие контейнеры не трогал.
- Правила GitHub (шаг 9) и стоп-кран (шаг 11) не проверялись: стенд без GitHub и без бота.
- В `packages/` ничего не менялось. Вопрос по пробелу 7 — решение владельца набора (код пакета doctor).
