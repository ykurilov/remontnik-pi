# Контракт: команды приложения для врача

Команды из `remontnik.config.ts` (`deploy.commands`, `checks.*`). Врач запускает их сам, в рабочей копии правки или основной ветки, на сервере приложения. Каждая команда идемпотентна или безопасна для повтора.

## Выкатка

| Команда | Вход | Выход и код | Требование |
|---|---|---|---|
| `build` | папка рабочей копии правки, `REMONTNIK_VERSION=<sha>` | 0 = собран кандидат | не трогает работающую версию; код правки выполняет только внутри сборки контейнера |
| `promote` | — | 0 = кандидат работает | до запуска сохраняет текущую сборку как прежнюю |
| `confirm` | — | 0 | снимает отметку «выкатка не подтверждена» |
| `rollback` | — | 0 = работает прежняя сборка | работает без git и без сети |
| `current` | — | stdout: JSON `{ "version": "<sha>", "previous": "<sha>" \| null }` | версия, которая реально работает; `previous` — есть ли сохранённая прежняя сборка. Версия — полный sha из 40 строчных шестнадцатеричных знаков, иначе ответ считается неизвестным |
| `health` | — | 0 = здоров, иначе нет; stdout — короткая причина | ответ не дольше 30 с |

Порядок выкатки врачом: стоп-кран → замок → снимок рабочей копии основной ветки → `current` (есть `version`) → метка git на `version` → `build` → сверка копии → `current` → стоп-кран → замок всё ещё свой → `promote` → `current` = кандидат → наблюдение (`health` и ошибки) → `confirm` → замок снят. Сбой на любом шаге после `promote` → `rollback` → `current` = прежняя → `health` → отчёт.

- `current` с `"version": null` значит «ещё ничего не выкатывали»: врач такую выкатку не начинает (откатываться некуда). Неизвестный ответ `current` до `promote` — отказ, после — откат.
- Работает кандидат брошенной выкатки (см. «Замок выкатки») — врач не выкатывает (`unconfirmed_version`, нужен человек): эту версию никто не подтверждал, и откатываться на неё нельзя. Блок снимает владелец, проверив версию: `remontnik-doctor deploys confirm <версия>` или `POST /v1/control/deploys` `{ action: "confirm_version" }` с подписью секретом владельца (`contracts/doctor-api.md`).
- Время выкатки (`promotedAt`) и конец окна наблюдения отсчитываются, когда `current` подтвердил кандидата, а не когда начался `promote`. Ошибки кандидата считаются раньше — с минуты, когда `promote` вернулся (`promoteReturnedAt`).
- `promote` повторяется после перезапуска врача, только если `current` всё ещё прежняя версия, замок — этой выкатки, а стоп-кран не нажат. Иначе отказ без `promote`: `lock_lost` (нужен человек) или `stop_switch`.
- Если после `promote` `current` показывает прежнюю версию, приложение само вернулось назад: это откат с причиной «приложение вернулось к прежней версии», а не выкатка человека. Другая версия — выкатка человека, врач её не трогает.
- Время на команду: `build` — 30 мин, `promote`/`confirm`/`rollback` — 5 мин, `current`/`health` — 30 с.

### Сборка

- `build` идёт в рабочей копии правки, а код правки выполняется только внутри сборки контейнера. Dockerfile и всё, что задаёт сборку, `build` берёт из основной ветки, а не из правки: правка их не меняет.
- Окружение `build` — только список: `PATH`, `HOME` (пустая временная папка, удаляется после сборки), `REMONTNIK_VERSION` и имена из `deploy.buildEnv`. Остальное окружение врача, в том числе секреты, `build` не видит.
- Остальные команды выкатки получают окружение врача без его секретов: имена с `REMONTNIK_`, `KEY`, `TOKEN`, `SECRET`, `PASS`, `AUTH`, `CREDENTIAL`, `PRIVATE`, `URL`, `DSN`, `COOKIE`, `SESSION` убираются. Всё, что нужно команде, она берёт из своих файлов на сервере.

### Рабочая копия основной ветки

Из неё идут `promote`, `confirm`, `rollback`, `current` и `health`. Взяв замок, врач снимает её отпечаток: коммит, изменённые и новые файлы по `git status` (кроме файла замка) с sha256 каждого и sha256 файлов `remontnik.config.*` в корне и скриптов, названных в `deploy.commands`, в том числе не попавших в git.

- Копия грязная уже в начале — врач не выкатывает (`main_copy_changed`, нужен человек).
- Дальше копия сверяется со снимком начала: тот же коммит, те же отпечатки настройки и скриптов, нет новых изменённых файлов, и у известных тот же sha256.
- Перед `promote` копия не та — отказ без `promote`.
- После `promote` перед каждой командой копия не та — откат. Откат идёт и дальше, даже если копия так и осталась изменённой; отчёт зовёт человека и начинается с пометки «ВНИМАНИЕ».
- Файлы состояния, которые пишут `promote` и `rollback` (отметки версий, журналы), должны быть в `.gitignore` приложения. Если всё же нет: изменённые файлы, появившиеся или изменившиеся за время своего `promote` или `rollback`, врач вносит в снимок вместе с sha256 и чужой правкой не считает; их следующая правка — уже изменённая копия. После падения врача так принимаются только файлы `promote`, о запуске которого есть запись (её врач делает прямо перед запуском), и только прерванного `rollback`. Коммит и отпечатки настройки и скриптов так не принимаются никогда.

### Наблюдение

- Тик раз в `observe.tickSeconds`. Каждый тик: `current`, `health`, ошибки с момента выкатки и за последние 10 минут.
- Откат по здоровью: 3 сбоя подряд или 3 сбоя среди последних `observe.healthWindowTicks` проверок. Сбой на последней проверке окна — тоже откат.
- Окно закрывается не раньше, чем пройдёт `observe.healthWindowTicks` проверок: одной проверки мало. Если врач не проверял дольше окна (спал, был выключен), окно начинается заново.
- Рост ошибок считается по всему окну и отдельно за последние 10 минут: короткий всплеск в конце окна тоже откатывает.

### Откат

- `rollback` повторяется до 3 раз. Считаются только законченные попытки: попытка, прерванная перезапуском врача, повторяется и не тратит счёт.
- Между попытками пауза растёт: 10 с, 30 с, 90 с. После третьей неудачной — пауза 90 с и ещё одна проверка `current`: вернулась прежняя — откат удался, нет — `rollback_failed`.
- Каждый запуск `rollback` записывается до запуска (`rollbackLaunches`). Больше 6 запусков, считая прерванные, — врач падает на самом откате: `rollback_failed`, нужен человек.

## Замок выкатки (`deploy.lockFile`)

Один файл на приложение, путь — от корня рабочей копии основной ветки или абсолютный. Его держит любая выкатка: врача и ручная.

- Ручной скрипт создаёт файл только если его нет (`set -o noclobber` или `mkdir`-подобная атомарная операция) и удаляет в конце. Содержимое — любое, кроме строки врача. Пустой файл — тоже замок человека.
- Врач пишет `remontnik deployment <id> <знак> <время ISO>`: `<знак>` — случайная метка из записи выкатки. Файл появляется целиком: врач пишет временный файл рядом и ставит его на место замка через жёсткую ссылку, только если замка нет.
- Чужой замок врач не трогает и ждёт, проверяя раз в 30 с. Своим он считает только замок, чьи номер и знак есть в его записях.
- Свой замок брошенной выкатки (закончилась, или умерла её задача) врач снимает так: переименовывает файл, сверяет содержимое и только потом удаляет. Если замок успели сменить, возвращает его на место. Если и место уже заняли, увезённый замок не удаляется, а остаётся рядом как `<замок>.lost-*`, и врач зовёт человека отчётом `needs_human`: чужой замок не пропадает никогда.
- Если врач упал, пока замок был уведён для сверки, рядом остаётся `<замок>.stale-*`, и замок человека мог остаться только в нём. Пока такой файл есть, врач замок не берёт и выкатку не начинает: один раз зовёт человека отчётом `needs_human` с путём к файлу и ждёт. Человек удаляет файл или возвращает его на место замка.
- Выкатка, чья задача умерла, помечается `abandoned`, человек получает отчёт `needs_human`. Если она успела записать намерение `promote`, её кандидат запоминается: пока он работает, новых выкаток нет (`unconfirmed_version`).
- После `promote` перед каждым действием с приложением (наблюдение, откат, `confirm`) врач проверяет, что замок всё ещё его. Потерян — выкатка `abandoned`, приложение он больше не трогает, нужен человек. Её кандидат запоминается так же, как у выкатки с умершей задачей (`unconfirmed_version`).
- Ждёт дольше `deploy.lockWaitReportMinutes` — один раз зовёт человека отчётом `needs_human` с путём к замку и его содержимым и ждёт дальше.

## Проверки

- `checks.test`: код 0 = зелёные. В stdout желательно сводка в формате JUnit XML или строка `REMONTNIK_FAILED=<имя>;<имя>` для списка упавших; иначе врач показывает хвост вывода.
- `checks.eval.run`: шаблон с подстановками `{scenarios}` (через запятую), `{repeat}`, `{maxCostUsd}`, `{outDir}`. Закрытые сценарии запускаться не должны — врач их и не передаёт.
- Тесты, проверка типов и eval идут во внутренней сети без выхода наружу. В ней только прокси модели врача и службы тестов из `checks.services`.
- Eval ходит к модели через прокси врача: адрес — в `baseUrlEnv` каждого `checks.eval.providers`, разовый пропуск — в его `keyEnv` и в `tokenEnv`. Настоящих ключей в контейнере нет.
- Прокси пропускает только `POST` на `chat/completions`, `messages`, `responses` и `embeddings` (с `/v1` или без) и только модели из `models` поставщика; остальное — `403`. Тело — JSON-объект не больше `checks.eval.proxy.maxRequestBytes`, иначе `400` или `413`. Лишний одновременный запрос — `429`.
- Если в запросе нет предела ответа (`max_tokens`, `max_completion_tokens`, `max_output_tokens`), прокси вставляет `checks.eval.proxy.maxOutputTokens`. Потоковому чату он добавляет `stream_options.include_usage`, чтобы посчитать расход.
- Запрос, чья наибольшая цена не влезает в остаток доли случая (`limits.evalUsdPerCase`), получает `402`, и прогон eval прерывается. Eval, который закончился штатно без единого `402`, принимается, даже если расход дошёл до доли.
- Скрипты и настройки eval берутся из основной ветки. Правка, которая их трогает, eval не проходит и уходит человеку.

## Итог eval `{outDir}/<resultFile>`

```json
{
  "scenarios": [
    { "id": "string", "repeats": 3, "pass": 2, "fail": 1, "standBroken": 0, "personaBroken": 0 }
  ],
  "costUsd": 0.12
}
```

`costUsd` врач не читает: расход eval он берёт у своего прокси. Поле можно не писать.

Если у приложения другой формат — его агент добавляет маленький переводчик в свою команду eval. Врач другие форматы не разбирает.
