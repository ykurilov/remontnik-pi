# Подключение Ремонтника к приложению

Инструкция для агента приложения. Пройдите шаги по порядку. Каждый шаг кончается проверкой: она прошла — переходите к следующему.

Ремонтник код приложения не правит: всё ниже делает агент приложения в своём репозитории и на своём сервере. Полный список того, что приложение обязано дать, — [contracts/app-integration.md](../specs/001-self-healing-kit/contracts/app-integration.md). Все поля настройки — [configuration.md](./configuration.md). Что и почему закрыто — [security.md](./security.md).

Сначала спросите владельца только то, чего нельзя узнать из кода:

- где хранилище приложения: GitHub или своё хранилище на сервере (шаг 9), и имя основной ветки;
- сервер приложения и как там идёт ручная выкатка (скрипт, compose);
- чат Telegram для тревог и бот, от имени которого они идут;
- нужен ли браузер врача и режим «сначала Paseo».

Всё остальное — из кода приложения.

## 1. Пакеты

```sh
pnpm add @ykurilov/remontnik-watch @ykurilov/remontnik-core
```

Пакеты появятся в npm с выпуском 0.1.0. Пока выпуска нет, эта команда вернёт `404`: спросите владельца набора, как подключить пакеты, и вернитесь к шагам ниже. Версии — точные, как во всём проекте.

Врач (`@ykurilov/remontnik-doctor`) в приложение не ставится: он работает отдельным контейнером (шаг 7). Для теста полного цикла (шаг 14) его ставят в разработку: `pnpm add -D @ykurilov/remontnik-doctor`.

Рабочий образец приложения со сторожем, командами выкатки и тестом цикла лежит в [`examples/`](../examples/README.md). Сверяйтесь с ним, если текст ниже неясен.

## 2. Сторож в коде

Сторож ловит падения и плохие ответы бота и шлёт их врачу. Он ставится в каждый процесс приложения: веб, фоновый работник и так далее.

```ts
import { createWatch } from '@ykurilov/remontnik-watch'

export const watch = createWatch({
  appName: 'my-app',                      // то же, что app.name в remontnik.config.ts
  processName: 'web',                     // у каждого процесса своё имя
  dir: process.env.REMONTNIK_WATCH_DIR!,  // папка очереди; общая для всех процессов приложения
  doctor: { url: process.env.REMONTNIK_DOCTOR_URL!, secret: process.env.REMONTNIK_SHARED_SECRET! },
  telegram: { botToken: process.env.APP_ALERT_BOT_TOKEN!, chatId: process.env.APP_ALERT_CHAT_ID! },
  release: process.env.REMONTNIK_VERSION ?? null,
})
watch.installProcessHandlers()
```

- `installProcessHandlers()` — сразу после создания: ловит `uncaughtException` и `unhandledRejection`. После записи процесс ведёт себя как без сторожа.
- **Упавший процесс сам сбой не доставит.** Сторож пишет сбой в очередь на диске, а врачу его отдаёт, когда процесс запустится снова. Значит, после падения приложение должно подняться само: `restart: unless-stopped` в Docker, systemd или другой перезапускатель. Без него случай у врача не появится.
- При штатной остановке: `await watch.flush(5000)`, затем `watch.close()`.
- Ручная запись сбоя: `watch.capture(error, { where: 'billing-sync' })`.
- Ошибки обращений к моделям: если приложение берёт модели из каталога Agent Chat SDK, оберните его `watch.wrapModelCatalog(catalog)`. Если модель вызывается иначе (прямой клиент, свой код), ловите ошибку сами: `watch.capture(error, { where: 'model:<имя модели>' })`.
- Очередь лежит в `REMONTNIK_WATCH_DIR` файлом `outbox-<processName>.jsonl` (рядом `.lock`). Папка должна переживать перезапуск процесса: том или каталог вне контейнера. Два живых процесса с одним `processName` не нужны: дайте им разные имена.
- `REMONTNIK_VERSION` — версия сборки, она привязывает сбой к выкатке. Её в окружение процесса приложения кладёт команда выкатки при запуске (`promote` и `rollback`): врач эту переменную им не передаёт. В образце [`remontnik-deploy.mjs`](../examples/mini-app/deploy/remontnik-deploy.mjs) это сделано в `startApp`. Без неё `release` будет `null`.
- В `.gitignore` приложения добавьте `.remontnik/` (замок выкатки) и папку очереди, если она внутри репозитория.
- `REMONTNIK_DOCTOR_URL` — `http://remontnik-doctor:7800`: врач слушает в сети Docker приложения (шаг 7). Приложение в сети сервера (`network_mode: host`) к сети Docker не подключить: у него `http://127.0.0.1:<REMONTNIK_HOST_PORT>`, по умолчанию `http://127.0.0.1:7800` (шаг 7).
- `createWatch` требует `dir`, `doctor.url`, `doctor.secret`, `telegram.botToken` и `telegram.chatId`. Если любое из них пустое (чаще всего не задана переменная окружения), он бросает `TypeError` с названиями пустых полей. Тесты, которые запускают процесс приложения, и локальный запуск должны задавать эти переменные (любые значения, свою папку очереди) — иначе приложение не стартует.
- Для подставного Telegram (тесты, стенд) в `telegram` есть необязательное поле `apiBaseUrl`; в боевом окружении его не задают.

**Agent Chat SDK.** Если в приложении стоит наш SDK чата, подключите хуки сторожа поверх своих:

```ts
import { agentChatWatchHooks } from '@ykurilov/remontnik-watch/agent-chat'

const hooks = agentChatWatchHooks(watch, { inner: appHooks, afterTurn: true })
```

`afterTurn: true` — только если хранилище SDK умеет `setAfterTurnState`. Иначе не включайте.

**Чтение разговоров.** Сторож может читать законченные разговоры и замечать плохие ответы бота. Для этого:

- в `createWatch` добавьте `model` (ключи DeepSeek и OpenRouter для сторожа — свои, не ключи приложения, см. шаг 6) и `review` (`botDescription` — что бот должен делать, `limits: config.limits` — дневной потолок `watchModelUsdPerDay`);
- там, где разговор закрывается, вызовите `watch.conversationFinished({ id, messages })`.

Проверка: тест приложения бросает ошибку в процессе со сторожем — в папке очереди появляется запись, `watch.stats()` показывает её в очереди. Врачу она уйдёт при следующем запуске процесса.

## 3. Настройка `remontnik.config.ts`

Файл в корне репозитория. Врач читает его только из основной ветки. Секретов в нём нет: только имена переменных окружения.

```ts
import { defineRemontnikConfig } from '@ykurilov/remontnik-core/config'

export default defineRemontnikConfig({
  app: { name: 'my-app', timeZone: 'UTC' },
  repo: { mainBranch: 'main' },
  workbench: { image: 'node:22', install: 'pnpm install --frozen-lockfile' },
  checks: { test: 'pnpm test', typecheck: 'pnpm typecheck' },
  evalScope: [],
  closedPaths: [],
  fixablePaths: ['src/**'],
  forbidden: {
    schema: ['src/db/schema/**', 'migrations/**'],
    money: ['src/billing/**'],
    access: ['src/auth/**'],
  },
  deploy: {
    commands: {
      build: 'node deploy/remontnik-deploy.mjs build',
      promote: 'node deploy/remontnik-deploy.mjs promote',
      confirm: 'node deploy/remontnik-deploy.mjs confirm',
      rollback: 'node deploy/remontnik-deploy.mjs rollback',
      current: 'node deploy/remontnik-deploy.mjs current',
      health: 'node deploy/remontnik-deploy.mjs health',
    },
    lockFile: '.remontnik/deploy.lock',
    buildEnv: [],                          // имена переменных, которые должен увидеть build (шаг 4)
  },
  reports: { telegram: { botTokenEnv: 'APP_ALERT_BOT_TOKEN', chatIdEnv: 'APP_ALERT_CHAT_ID' } },
})
```

Как заполнять:

- `forbidden.schema`, `money`, `access` — где у приложения схема базы, деньги и доступы. Найдите это в коде сами. Пустыми маски быть не могут: зоны нет — пишите `['<нет>']` с комментарием.
- `fixablePaths` — где врач может править код. Узко, только код приложения. Тесты, сборка, выкатка и файлы-замки сюда не входят.
- `closedPaths` — что врач не должен видеть вовсе: личные данные, выгрузки.
- `workbench.image` — образ с той же версией Node, что у приложения. `install` для npm — `npm ci`.
- Готовая настройка небольшого приложения — [`examples/mini-app/remontnik.config.mjs`](../examples/mini-app/remontnik.config.mjs).

Проверка: `remontnik.config.ts` входит в `include` вашего `tsconfig.json` (иначе `tsc` его не видит), `pnpm exec tsc --noEmit` проходит, а импорт файла не бросает `RemontnikConfigError`.

## 4. Команды выкатки

Врач выкатывает и откатывает командами приложения. Договор — [deploy-commands.md](../specs/001-self-healing-kit/contracts/deploy-commands.md). Коротко:

| Команда | Что должна делать |
|---|---|
| `build` | собрать кандидата из рабочей копии правки; версия — в `REMONTNIK_VERSION`. Код правки выполняется только внутри сборки контейнера. Работающую версию не трогает. Запоминает кандидата (например, в файле состояния): `promote` версии не получает |
| `promote` | взять кандидата, которого запомнил `build`, сохранить текущую сборку как прежнюю и запустить кандидата. Выйти с кодом 0, только когда кандидат уже отвечает: сразу после `promote` врач проверяет здоровье и страницы |
| `confirm` | снять отметку «выкатка не подтверждена» |
| `rollback` | вернуть прежнюю сборку, без git и без сети |
| `current` | напечатать `{"version":"<полный sha>","previous":"<sha>"\|null}` — что реально работает |
| `health` | код 0 — здоров; не дольше 30 секунд |

- Команды врач запускает внутри своего контейнера, в рабочей копии основной ветки (или в копии правки для `build`). Там есть `sh`, Node 22, `git` и клиент Docker с compose; нет `curl`, `pnpm` и пакетов приложения. Пишите команды на этом наборе. Папки и файлы, которые команды читают и пишут вне копии, смонтируйте в контейнер врача по тем же путям, что на хосте (том в `deploy/compose.remontnik.yml`).
- Смена ссылки на версию должна быть атомарной: сначала новая ссылка рядом, потом переименование поверх старой. На Linux это `mv -T`, на macOS — `mv -h`. Обычный `mv` на macOS, если старая ссылка ведёт в папку, кладёт новую внутрь папки.
- Замок `deploy.lockFile` — общий с ручной выкаткой. Врач держит его на время своей выкатки, поэтому команды под ним замок не берут. Ручной скрипт создаёт его атомарно (`set -o noclobber`) и удаляет в конце; пример — команда `deploy <sha>` в образце.
- **Ручная выкатка — только из закоммиченного состояния, в котором уже есть текущая удалённая основная ветка.** Врач кладёт свои правки в `origin/main`. Если выкатить сборку без них, правка врача пропадёт с сервера. Скрипт ручной выкатки сам отказывает, если есть незакоммиченные правки или `origin/<основная ветка>` не предок выкатываемого коммита. Версия выкатки — полный sha коммита:

  ```sh
  git fetch origin main
  test -z "$(git status --porcelain)" || { echo "есть незакоммиченные правки: сначала коммит" >&2; exit 1; }
  version=$(git rev-parse HEAD)
  git merge-base --is-ancestor origin/main "$version" || { echo "в выкатке нет текущей origin/main: сначала git pull" >&2; exit 1; }
  ```
- Файлы состояния, которые пишут `promote` и `rollback`, — в `.gitignore`.
- `build` видит только `PATH`, пустой `HOME`, `REMONTNIK_VERSION` и имена из `deploy.buildEnv`. Остальное он берёт из своих файлов на сервере. Имена `REMONTNIK_*` в `buildEnv` писать нельзя.
- Остальным командам врач передаёт своё окружение без секретов. Убираются все имена, которые начинаются с `REMONTNIK_` или содержат `KEY`, `TOKEN`, `SECRET`, `PASS`, `AUTH`, `CREDENTIAL`, `PRIVATE`, `URL`, `DSN`, `COOKIE` или `SESSION` (полный список — в [контракте](../specs/001-self-healing-kit/contracts/deploy-commands.md#сборка)). Поэтому `promote` не получит ни `REMONTNIK_VERSION`, ни адрес здоровья из окружения. Всё нужное команда берёт из своих файлов на сервере.
- **Как передать команде переменную.** Для `build` — имя в `deploy.buildEnv`, а значение должно быть в окружении контейнера врача (`REMONTNIK_ENV_FILE`). Для остальных команд — файл в папке выкаток, которая смонтирована в контейнер врача по тому же пути, что на хосте.
- **Как команды управляют приложением, ведь они идут в контейнере врача.** Они меняют файлы в папке выкаток и запускают, останавливают или перезапускают приложение. Образец [`remontnik-deploy.mjs`](../examples/mini-app/deploy/remontnik-deploy.mjs) хранит состояние в `APP_DEPLOY_DIR`: версии в `releases/<sha>`, ссылка `current`, `state.json`, переменные приложения в `app.env`, адрес здоровья в `settings.json`.
- **Образец запускает приложение процессом `node` внутри контейнера врача. Так годится только для стенда и теста.** В бою приложение запускают через `docker compose` (или systemd на хосте): замените `startApp`, `stopApp` и проверку процесса на вызовы `docker compose` (клиент и сокет Docker у врача есть). Тогда перезапускает упавшее приложение сам Docker (`restart: unless-stopped`), а команда `start` из образца не нужна.
- **Папка выкаток в контейнере врача.** `APP_DEPLOY_DIR` обязателен: без него образец отказывает с понятной ошибкой. Задайте переменную врачу и смонтируйте папку по тому же пути, что на хосте. Папка должна быть доступна на запись пользователю врача (uid 10001: `chown 10001:10001 <папка>`). Готовый `compose.override.yml` рядом с `deploy/compose.remontnik.yml`:

  ```yaml
  services:
    doctor:
      environment:
        APP_DEPLOY_DIR: /srv/my-app-deploy
      volumes:
        - /srv/my-app-deploy:/srv/my-app-deploy
  ```

  Запускайте с обоими файлами: `docker compose -f deploy/compose.remontnik.yml -f deploy/compose.override.yml up -d`. Переменная `APP_DEPLOY_DIR` для `build` дополнительно называется в `deploy.buildEnv`.

Проверка: на сервере вручную `build` → `promote` → `current` показывает новую версию → `rollback` → `current` показывает прежнюю.

## 5. Eval и службы для тестов

**Eval** — если у приложения есть сценарии с настоящей моделью. В `checks.eval`:

- `run` — шаблон команды с `{scenarios}`, `{repeat}`, `{maxCostUsd}`, `{outDir}`;
- `resultFile` — итог в формате договора;
- `scenariosDir` — папка сценариев, если не `eval/scenarios` (например, `evals/scenarios`). По ней `closedPaths` закрывают сценарии: без верной папки закрытый сценарий запустится;
- `providers` — модели, к которым eval ходит через прокси врача. Настоящий ключ лежит у врача под именем `keyEnv`. Eval получает в той же переменной разовый пропуск, а в `baseUrlEnv` — адрес прокси;
- `env` — только несекретные переменные.

Для eval заведите отдельный ключ модели с месячным лимитом у поставщика (шаг 6) и отдельную базу для прогонов. `evalScope` связывает пути кода со сценариями.

**Службы для тестов** — если тестам нужна база. Файл compose в репозитории, путь — в `checks.services`. Правила:

- образ закреплён по отпечатку: `postgres:17-alpine@sha256:<64 знака>` (отпечаток — `docker buildx imagetools inspect postgres:17-alpine`);
- без портов, томов, сетей и `env_file`; база — с `healthcheck`;
- вместо `$` пишите `$$`;
- файл не должен попадать в `fixablePaths`.

Тесты ходят к базе по имени службы (`db:5432`). Пример — в [configuration.md](./configuration.md#службы-для-тестов).

Проверка: `pnpm test` зелёный в чистой копии; `remontnik-doctor check-config` (шаг 8) не ругается на службы.

## 6. Окружение сервера

Секреты — только в окружении сервера. Ни в репозитории, ни в чате, ни в настройке их нет. Владелец передаёт их через `secret-handoff`: значение вводится в скрытом окне и ложится файлом на сервер. В инструкциях и отчётах — только имена.

Два файла окружения, оба с правами `0600`, вне репозитория.

**Врач** (`REMONTNIK_ENV_FILE`):

Секреты врача — общий, владельца и моста (раздел 13) — не короче 32 знаков, у каждого из трёх своё значение: `openssl rand -hex 32` отдельно на каждый. Иначе врач не стартует, а `check-config` назовёт, какие совпали или коротки.

| Переменная | Что это |
|---|---|
| `REMONTNIK_SHARED_SECRET` | общий секрет сторожа и врача; тот же — в окружении приложения. Не короче 32 знаков |
| `REMONTNIK_CONTROL_SECRET` | секрет владельца: снимает стоп-кран и «нужен человек». Не короче 32 знаков, отличается от общего. Приложению не выдаётся |
| `REMONTNIK_GIT_TOKEN` | ключ git врача на GitHub: только этот репозиторий, право записи, не личный ключ владельца |
| `REMONTNIK_GIT_SSH_KEY`, `REMONTNIK_GIT_KNOWN_HOSTS` | вместо токена, если хранилище своё (шаг 9): закрытый SSH-ключ врача и строка ключа сервера |
| `DEEPSEEK_API_KEY`, `OPENROUTER_API_KEY` | ключи модели врача |
| `APP_ALERT_BOT_TOKEN`, `APP_ALERT_CHAT_ID` | бот и чат тревог: имена — из `reports.telegram`. Бот — тот же, что у приложения |
| ключи из `checks.eval.providers[].keyEnv` | настоящие ключи моделей для eval |
| значения из `checks.eval.providers[].upstreamHeaders[].valueEnv` | если заданы: секреты дополнительных заголовков к поставщику модели |
| `REMONTNIK_REPORTS_TOKEN` | по желанию: забор отчётов командой по SSH |
| `REMONTNIK_BROWSER_TOKEN` | если есть браузер врача |

**Приложение**: `REMONTNIK_SHARED_SECRET`, `REMONTNIK_DOCTOR_URL`, `REMONTNIK_WATCH_DIR`, бот и чат тревог.

- **Ключи моделей Ремонтника — свои, не ключи приложения.** Отдельный ключ у сторожа, у врача и у eval. У поставщика на каждом стоит месячный лимит, по умолчанию 10 $. Это последняя преграда, если суточные потолки `limits` не сработают.
- **Бот тревог — тот же бот, что у приложения.** Сторож и врач пишут от его имени, а нажатия кнопок получает приложение и передаёт сторожу (шаг 11). У отдельного бота нажатие «Остановить автовыкатку» до сторожа не дойдёт.

Несекретные настройки контейнера врача (`REMONTNIK_APP_DIR`, `REMONTNIK_STATE_DIR`, `REMONTNIK_APP_NETWORK`, `DOCKER_GID` и другие) — в `.env` рядом с файлом compose. Список — в шапке [`deploy/compose.remontnik.yml`](../deploy/compose.remontnik.yml).

## 7. Врач на сервере

1. На сервере — рабочая копия основной ветки приложения (`REMONTNIK_APP_DIR`). Это чистый клон основной ветки из удалённого репозитория (`git clone`; у своего хранилища — клон этого хранилища, [security.md](security.md#рабочая-копия-врача)), а не копия файлов с компьютера разработчика. Руками в ней не правят и ручную выкатку из неё не делают: в ней работает врач. Копия — чистый git-репозиторий на основной ветке (`REMONTNIK_MAIN_BRANCH`, по умолчанию `main`), читаемый пользователем врача (по умолчанию uid и gid `10001`, `REMONTNIK_UID` и `REMONTNIK_GID`). Врач читает настройку из неё и выкатывает из неё. Зависимости приложения в ней ставить не нужно. Настройка — это код. Врач выполняет его не у себя, а в отдельном контейнере из своего образа: без своих секретов, без сокета Docker, без сети, только с копией файлов настройки (подробно — [`docs/security.md`](security.md#чтение-настройки)). Из настройки и её соседних файлов можно подключать: пакеты Ремонтника, которые есть у врача (сейчас только `@ykurilov/remontnik-core`; `@ykurilov/remontnik-watch` у врача нет), встроенные модули Node и свои файлы по относительному пути строкой в кавычках. Любой другой пакет, абсолютный путь, выход за пределы репозитория и импорт с вычисляемым путём дают понятную ошибку. Всё, что подключает настройка, врач не правит: правка такого файла — только отчёт человеку. Поэтому не подключайте из настройки код приложения (`src/**`), который врач должен чинить. Общий с настройкой текст держите в `remontnik.config.<имя>.ts`. `check-config` предупреждает, если настройка подключает файл из `fixablePaths`.
2. Сеть Docker приложения должна уже существовать: compose её не создаёт, а только подключает врача (`docker network create <имя>`, если приложение сети ещё не завело). Имя сети — `REMONTNIK_APP_NETWORK`, и сторож ходит к врачу в ней: `REMONTNIK_DOCTOR_URL` — `http://<имя контейнера врача>:7800`. Имя контейнера врача — `REMONTNIK_CONTAINER_NAME` (по умолчанию `remontnik-doctor`); если на хосте уже есть другой врач, задайте другие `REMONTNIK_PROJECT`, `REMONTNIK_CONTAINER_NAME` и `REMONTNIK_OUTSIDE_NETWORK`. Файл [`deploy/compose.remontnik.yml`](../deploy/compose.remontnik.yml) собирает образы из корня репозитория Ремонтника (`context: ..`), поэтому запускайте его из клона этого репозитория, а не из копии одного файла. Переменные из его шапки задайте в оболочке, в `.env` рядом с файлом или ключом `--env-file`. `DOCKER_GID` на Linux — `stat -c %g /var/run/docker.sock`; в Docker Desktop на Mac сокет принадлежит группе `0`.
3. Запустите из корня репозитория Ремонтника:

   ```sh
   docker compose -f deploy/compose.remontnik.yml up -d --build
   ```

Врач подключается к сети Docker приложения и слушает порт 7800 только там. Наружу порт не публикуется.

**Приложение в сети сервера (`network_mode: host`).** Такое приложение к сети Docker не подключить. Для него есть добавка [`deploy/compose.remontnik.host-app.yml`](../deploy/compose.remontnik.host-app.yml):

- сеть приёма создаёт сам Ремонтник, в ней только врач. Её имя — в `REMONTNIK_APP_NETWORK` (например, `remontnik-intake`); заранее её не создают;
- врач публикует приём только на `127.0.0.1` сервера, порт — `REMONTNIK_HOST_PORT` (по умолчанию 7800);
- у сторожа `REMONTNIK_DOCTOR_URL=http://127.0.0.1:<REMONTNIK_HOST_PORT>`;
- нужен Docker 28 или новее: добавка ставит сети приёма `gw_priority`, иначе порт ведёт не туда, где слушает врач.

```sh
docker compose -f deploy/compose.remontnik.yml -f deploy/compose.remontnik.host-app.yml up -d --build
```

Этот же второй `-f` добавляйте ко всем командам `docker compose` ниже. Приём по-прежнему закрыт от браузера врача, от сетей случая и снаружи сервера.

## 8. Проверка настройки

```sh
docker compose -f deploy/compose.remontnik.yml exec doctor remontnik-doctor check-config
```

Запускайте только так, внутри контейнера врача. С хоста из `node_modules` приложения настройку не прочитать: `check-config` скажет «врач запущен не из своего контейнера» и подскажет эту команду.

Врач уже запущен (шаг 7): проверка ищет его контейнер по имени `REMONTNIK_CONTAINER_NAME` (по умолчанию `remontnik-doctor`), а одноразовый контейнер `run --rm` называется иначе и проверку Docker не проходит.

Команда проверяет всё, на чём споткнётся старт врача:

- настройку основной ветки;
- файлы команд выкатки: они есть, у прямо запускаемых есть бит исполнения, скрипты на `node` и `sh` разбираются. Сами команды проверка не запускает;
- переменные окружения — все недостающие сразу;
- что секрет владельца отличается от общего;
- Docker и сети случая; у приложения в сети сервера — что приём опубликован только на `127.0.0.1` и порт ведёт в сеть приёма;
- закрепление образов служб;
- защиту origin: правила GitHub, если есть `gh`, или настройки и хук своего хранилища.

Ответ — список «что не так — как исправить». Код выхода не нулевой, если есть ошибки. Секретов и адресов в выводе нет. Исправляйте, пока не будет «ошибок нет».

## 9. Защита хранилища

Врач может добавлять ветки и метки, но не стирать и не переписывать. Это держит само хранилище приложения. Подходят два вида.

**GitHub.** Правила репозитория из [`deploy/github-ruleset.json`](../deploy/github-ruleset.json). Применяет владелец через `gh`, вошедший под его именем:

```sh
jq -c '.[]' deploy/github-ruleset.json | while read -r ruleset; do
  printf '%s' "$ruleset" | gh api --method POST /repos/OWNER/REPO/rulesets --input -
done
gh api /repos/OWNER/REPO/rulesets
```

Последняя команда показывает оба набора с `enforcement: active`. Повторный запуск создаёт дубликаты; обновление — `PUT` на `/repos/OWNER/REPO/rulesets/ID`. `check-config` проверяет правила сам.

**Своё хранилище на сервере.** Bare-репозиторий на том же сервере под пользователем git с git-shell. Врач пишет в него по SSH своим ключом, токен не нужен. Рецепт целиком — [security.md, «Своё хранилище на сервере»](security.md#своё-хранилище-на-сервере). Коротко:

1. root на сервере заводит пользователя git и хранилище: `receive.denyNonFastForwards` и `receive.denyDeletes` включены, хук [`deploy/git-update-hook`](../deploy/git-update-hook) стоит в `hooks/update`, config и хук принадлежат root.
2. Ключ врача — в `authorized_keys` с `restrict,command="remontnik-git doctor <путь хранилища>"`, ключ человека — с `restrict,command="remontnik-git person <путь хранилища>"`. Закрытая часть ключа врача — в `REMONTNIK_GIT_SSH_KEY`, строка ключа сервера — в `REMONTNIK_GIT_KNOWN_HOSTS`.
3. Человек кладёт код со своего компьютера своим ключом: `git push` по SSH. Его копия — заодно запасная копия хранилища.
4. `REMONTNIK_APP_DIR` — клон хранилища, origin — `ssh://git@host.docker.internal/<путь>.git`. Имя `host.docker.internal` — это сервер со стороны контейнера врача, его даёт шаблон compose.

`check-config` проверяет настройки, хук, роль ключа врача и его привязку к хранилищу по SSH и ничего не записывает. Что хук и config принадлежат root, по SSH не проверить: об этом всегда будет предупреждение с командой для root.

## 10. Правила приложения

Конституция, `AGENTS.md`, `CLAUDE.md` и прочие правила приложения не должны запрещать автоматическую выкатку врачом. Если запрещают, согласуйте правку с владельцем.

## 11. Стоп-кран

Под отчётами врача о выкатке и о готовой правке стоит кнопка «Остановить автовыкатку». Бот тревог принадлежит приложению, поэтому нажатие приходит к нему (webhook или опрос). Приложение передаёт нажатие сторожу:

```ts
// В обработчике обновлений бота тревог (webhook или опрос), до своих кнопок:
if (update.callback_query) {
  const answer = await watch.handleStopButton(update.callback_query)
  if (answer !== null) {
    await bot.answerCallbackQuery(update.callback_query.id, { text: answer })
    return
  }
}
```

`handleStopButton` проверяет, что нажали в чате тревог, и отправляет врачу подписанный общим секретом стоп. Он возвращает текст для ответа на нажатие или `null`, если кнопка не его. Бросать он не умеет: при сбое в тексте будет совет остановить из консоли.

Если в приложении нет объекта бота (обновления приходят вебхуком на ваш адрес), ответ на нажатие можно вернуть прямо в ответе на вебхук: Telegram выполнит его как вызов метода.

```ts
const answer = await watch.handleStopButton(update.callback_query)
if (answer !== null) return { method: 'answerCallbackQuery', callback_query_id: update.callback_query.id, text: answer }
```

Пример целиком — `alertBotUpdate` в [`examples/mini-app/src/main.js`](../examples/mini-app/src/main.js).

Остановить из консоли сервера:

```sh
docker compose -f deploy/compose.remontnik.yml exec doctor remontnik-doctor deploys stop --by owner
```

Снова пустить выкатки — `deploys resume`, только с секретом владельца. Кнопкой этого сделать нельзя.

Проверка: нажмите кнопку под любым отчётом о выкатке. Бот ответит «Автовыкатка остановлена», а следующий отчёт придёт без кнопки, с припиской «Стоп-кран включён».

## 12. Браузер врача (по желанию)

Нужен, если врачу надо смотреть страницы приложения.

1. Учётка Ремонтника в кабинете приложения — отдельная, с минимальными правами.
2. Политика браузера (`browser-policy.json`) — отдельный файл на сервере, путь к нему — в `REMONTNIK_BROWSER_POLICY`. Это не `remontnik.config.ts`: файл читает служба браузера. В нём только сайты приложения в `allowedOrigins` и узкие `allowedMutations`. Агент приложения при подключении составляет список `extraOrigins` и вписывает его сюда: сторонние адреса, с которых страницы грузят картинки, скрипты и шрифты (CDN), без счётчиков аналитики. После входа паролем всё остальное не грузится. Образец файла — в [packages/browser/README.md](../packages/browser/README.md).
3. В `remontnik.config.ts` — раздел `browser`: `enabled`, `profile`, те же `allowedOrigins` и `allowedMutations`, `pagesToCheck`, `loginEntryId`. Поля `extraOrigins` в нём нет: вписанное туда — ошибка «неизвестное поле». Все поля — в [configuration.md](./configuration.md#browser--браузер-врача).
4. Ключи браузера (`REMONTNIK_BROWSER_TOKEN`, `REMONTNIK_BROWSER_VAULT_KEY`) — через `secret-handoff` в `REMONTNIK_BROWSER_ENV_FILE`.
5. Запуск: `docker compose -f deploy/compose.remontnik.yml --profile browser up -d --build`.
6. Вход сохраняет владелец в консоли сервера. Пароль — только через стандартный ввод, в аргументах и журналах его нет:

   ```sh
   docker compose -f deploy/compose.remontnik.yml exec -T browser \
     remontnik-browser logins add --site https://app.example.com --login remontnik@example.com --profile remontnik --password-stdin < password-file
   ```

   Номер входа (команда `logins list`) — в `browser.loginEntryId` настройки.

Пароль короче 8 знаков не сохраняется. Как пароль скрыт от модели — в [security.md](./security.md#пароли-браузера).

**Вход через сервис авторизации.** Часто форма входа живёт на другом сайте, и пароль уходит методом `POST` туда. Тогда:

- сайт сервиса авторизации — в `allowedOrigins` политики и настройки, рядом с сайтом приложения;
- сохранённый вход заводится на точный сайт сервиса: `--site` — адрес сервиса, а не приложения;
- в `allowedMutations` — только путь формы входа и с полем `origin` сервиса: `{ "method": "POST", "pathPattern": "/login", "origin": "https://auth.example.com" }`. Так этот путь открыт только на сервисе. Правило без `origin` действует на всех сайтах из `allowedOrigins`;
- подтверждение кодом из письма или SMS врач не проходит. Такая учётка не годится: нужна учётка со входом только по паролю.

`origin` вне `allowedOrigins` отклоняют служба браузера при старте и `check-config`.

**Служебный вход по ключу — когда пароля нет.** Если в приложение входят только через Google, код из письма или SMS, агент приложения при подключении делает Ремонтнику свой вход:

- в приложении — страница входа для учётки Ремонтника с одним полем `type="password"` и `POST` на свой путь. Верный ключ открывает сеанс только этой учётки, с минимальными правами. Ключ сверяется с хешем из окружения сервера приложения, перебор ограничен. Пути этого входа — в `forbidden.access`: врач их не правит;
- ключ (не короче 32 случайных знаков) агент создаёт на сервере сам и сразу отдаёт в два места: хеш — в окружение приложения, сам ключ — в `logins add … --password-stdin` службы браузера (`--site` — сайт приложения). В чат, файлы, аргументы и журналы ключ не попадает, человека не зовут;
- в `allowedMutations` — только путь этой формы с `origin` приложения; номер входа — в `browser.loginEntryId`.

Отключить вход — сменить или убрать хеш в окружении приложения.

## 13. Режим «сначала Paseo» (по желанию)

В этом режиме врач сначала отдаёт случай агенту приложения в Paseo на компьютере владельца. Тот чинит по своим правилам. Не взял или не смог — врач лечит сам. Наблюдение и откат врач делает в любом случае. Договор — [paseo-bridge.md](../specs/001-self-healing-kit/contracts/paseo-bridge.md).

1. Частная сеть между сервером и компьютером владельца (например, Tailscale).
2. Мост `@ykurilov/remontnik-paseo-bridge` — плагин Paseo на компьютере владельца. Настройка — `~/.config/remontnik/paseo-bridge.json`: адрес частной сети, агент приложения, адрес врача, файл с секретом моста.
3. В настройке приложения:

   ```ts
   handoff: {
     mode: 'paseo-first',
     paseo: { bridgeUrlEnv: 'REMONTNIK_BRIDGE_URL', bridgeSecretEnv: 'REMONTNIK_BRIDGE_SECRET', listenEnv: 'REMONTNIK_BRIDGE_LISTEN' },
   },
   ```

4. Секрет моста — через `secret-handoff` в окружение врача и в файл моста. Не короче 32 знаков и свой: у каждого из трёх секретов (общий, владельца, моста) своё значение, иначе врач не стартует. Сгенерировать: `openssl rand -hex 32` — отдельно для каждого. Адрес моста и адрес врача в частной сети — тоже в окружение врача.

Агент приложения отчитывается командами `remontnik-paseo accept | done | cannot` с ключом задачи из письма моста (`REMONTNIK_PASEO_KEY`); секрета моста у агента нет. Частная сеть, правила доступа, порт врача в Docker и секрет моста по шагам — [operations.md](./operations.md#режим-сначала-paseo).

## 14. Проверка всего цикла без настоящей модели

Нужна, чтобы убедиться, что сбой доходит до врача, правка выкатывается и приложение выздоравливает, без денег и сети. Врач в тесте запускается в процессе теста, его модель подставная; сторож, git и команды выкатки настоящие.

- Пакет `@ykurilov/remontnik-doctor` ставится в разработку (`pnpm add -D`), не в приложение. Подставная модель и готовая настройка — `@ykurilov/remontnik-doctor/testing` (`createScriptedModel`, `callTool`; [README врача](../packages/doctor/README.md#для-тестов)). Подставной Telegram — `startFakeTelegram` из `@ykurilov/remontnik-core/testing`.
- Образец полного цикла «сбой → правка → выкатка → `healed`» — [`examples/cycle-test/crash-cycle.test.ts`](../examples/cycle-test/crash-cycle.test.ts): `startDoctorService` с `createLocalRunner()` и `allowUnisolatedRunner: true` (только для тестов), `createGitGuard`, `createServerDeployer` с вашими командами выкатки, часы врача (`onWake`), которые перескакивают окно наблюдения. Аргументы `finish_diagnosis` и `finish_fix` и остальные инструменты модели описаны в README врача.
- Тест копирует ваше приложение в чистый git-репозиторий. Сам тест цикла в копию не кладите (иначе он запустит сам себя), а `tsconfig.json` копии не должен наследовать файл вне копии.
- Подставная модель правит код по сценарию. Существующие тесты приложения правка менять не может, поэтому тест, который закрепляет сам сбой как ожидаемое поведение, провалит выкатку: такие тесты уберите или перепишите заранее.
- После падения процесса тест должен сам сыграть роль перезапускателя (в образце — команда `start` скрипта выкатки): без запуска сбой не дойдёт до врача.

## Готово, когда

- `check-config` пишет «ошибок нет»;
- тестовый сбой в приложении приходит врачу и в Telegram;
- ручной `rollback` возвращает прежнюю версию.
