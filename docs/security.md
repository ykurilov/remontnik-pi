# Безопасность врача

Врач правит код приложения, поэтому у него есть доступ к git. Этот доступ узкий: врач может добавлять, но не может стирать и переписывать. Держится это двумя замками: правами на GitHub и проверкой в коде врача (`git-guard`).

## Что может врач

- Создавать свои ветки `remontnik/<номер-случая>-<коротко>` и отправлять в них правки.
- Ставить свои метки `remontnik/pre-deploy/<дата>-<номер>` на прежнюю рабочую версию перед выкаткой.
- Влить свою правку в основную ветку обычным слиянием, но только после окна наблюдения и только если в настройках включено `repo.mainline: "merge"`.

## Чего врач не может

- Переписывать историю.
- Писать в основную ветку принудительно (force-push).
- Удалять ветки и метки.
- Двигать или заменять метки `remontnik/**` после создания.

## Шаблон правил GitHub

Шаблон лежит в [`deploy/github-ruleset.json`](../deploy/github-ruleset.json). Это список из двух наборов правил, потому что GitHub не смешивает ветки и метки в одном наборе:

1. Основная ветка: запрещены принудительная запись (`non_fast_forward`) и удаление (`deletion`). Обычная запись и слияние разрешены.
2. Метки `remontnik/**`: запрещены изменение (`update`) и удаление (`deletion`). Новые метки создавать можно.

Обходов (`bypass_actors`) в шаблоне нет: правила действуют на всех, включая владельца репозитория. Если владельцу нужно один раз что-то исправить вручную, он на время отключает набор правил в настройках репозитория и включает обратно.

### Как применить

Нужен `gh`, вошедший под владельцем репозитория, и `jq`. `OWNER/REPO` — ваш репозиторий приложения.

```sh
jq -c '.[]' deploy/github-ruleset.json | while read -r ruleset; do
  printf '%s' "$ruleset" | gh api --method POST /repos/OWNER/REPO/rulesets --input -
done
```

Повторный запуск создаст дубликаты. Чтобы обновить уже созданный набор, возьмите его номер из `gh api /repos/OWNER/REPO/rulesets` и отправьте тело методом `PUT` на `/repos/OWNER/REPO/rulesets/ID`.

Проверка: `gh api /repos/OWNER/REPO/rulesets` показывает оба набора со значением `enforcement: active`.

## Ключ git врача

- Ключ отдельный, не личный ключ владельца.
- Доступ только к одному репозиторию приложения (deploy-ключ с правом записи или токен, ограниченный этим репозиторием).
- Хранится только в окружении сервера, передаётся через `secret-handoff`. В репозиторий, чат и отчёты он не попадает.
- Права владельца репозитория (администратора) ключу не нужны: правила GitHub применяются под его именем так же, как под любым другим.

## Eval и ключи моделей

Eval прогоняет сценарии приложения с настоящей моделью. Код правки при этом пишет модель-врач, поэтому eval считается чужим кодом: ключи ему не доверяют.

### Прокси модели

- Настоящие ключи моделей лежат только у врача. В контейнер eval они не попадают.
- На каждый прогон eval врач открывает прокси и выдаёт разовый пропуск. Eval получает адрес прокси в `baseUrlEnv` и пропуск вместо ключа в `keyEnv`.
- Прокси подставляет настоящий ключ, считает расход каждого ответа и отвечает `402`, когда доля случая (`limits.evalUsdPerCase`) кончилась.
- Запросы ходят только под адрес `upstream` своего поставщика. Попытка выйти выше по пути получает `400`.
- Расход в журнал трат пишет врач со слов прокси. Цифре `costUsd` из итога eval он не верит.
- Перед прогоном врач бронирует долю случая. Если прогон оборвался, бронь закрывается фактом прокси. Целиком сгорает только то, чего прокси не успел увидеть.
- В `checks.eval.env` нельзя передать переменную с именем ключа, токена или пароля: настройка такую не примет.

### Внутренняя сеть проверок

- Тесты, проверка типов и eval идут в отдельной сети Docker без выхода наружу. В ней только прокси врача и службы тестов приложения из `checks.services`.
- Шлюз сервера, адрес метаданных облака и домашняя сеть из неё не видны.
- Установка зависимостей идёт в обычной сети: ей нужен реестр пакетов.
- Сеть создаёт служба врача (T129): `internal: true`, имя передаётся в `internalNetwork`, прокси — в `evalProxy { listen, publicUrl }`. Без `internalNetwork` проверки во внутренней сети отказываются запускаться.

### Что ещё держит eval честным

- Скрипты и настройки eval берутся из основной ветки. Правка, которая их трогает, eval не проходит и уходит человеку.
- Проверка правки ищет запись в файлы, чтение окружения, обращение к `outDir`, `REMONTNIK*` и файлу итога eval, новые адреса. Такая правка уходит человеку, а не на выкатку.

### Что остаётся

- Хитрую подделку итога eval, которую не поймала проверка правки, ловит окно наблюдения после выкатки (этап 6) и откат.
- Один запрос, или несколько одновременных, может перебрать долю случая на свою стоимость: прокси узнаёт цену только из ответа.
- Если врач упадёт между началом запроса и записью «запрос в пути», этот запрос может не попасть в журнал.
- Токены кэша прокси считает по цене обычного входа.
- Контейнеры модели-врача и установки пока в обычной сети `bridge`. Перевод их в закрытую сеть — T129.
- Локальный запуск без Docker сеть не ограничивает. Он только для разработки.
