## 0.1.7

### Patch Changes

- e3070a0: - **pnpm и yarn в образе без них.** В `node:22` pnpm нет, и установка pnpm-приложения падала с «pnpm: not found». Теперь врач сам кладёт в верстак заглушки `pnpm`, `pnpx` и `yarn` → `corepack <имя>`, если своих в образе нет, а corepack есть. `corepack enable` не нужен: корень контейнера только для чтения. Версия — из `packageManager` приложения. Её скачивает corepack через зеркало врача и сверяет подпись. Хранит её в HOME копии, поэтому команды проверок без сети её тоже видят. Своя программа образа важнее заглушки.
  - **Зеркало реестра отдаёт одну версию пакета** (`/pnpm/10.33.2`, `/@scope/name/1.0.0`): так corepack узнаёт адрес архива pnpm и yarn. Раньше такой путь получал 400.
  - **Предел метаданных пакета в зеркале — 256 МБ вместо 64.** Полные метаданные `@prisma/client` уже 68,5 МБ. pnpm 10 просит полный документ для необязательных зависимостей и в `pnpm view`. Ответ, как и раньше, идёт потоком и в памяти врача не копится. Защита от сжатых бомб, сроки и число одновременных ответов прежние.
  - **check-config проверяет pnpm и yarn в образе верстака.** Проверка срабатывает, когда pnpm, pnpx или yarn зовёт одна из команд `workbench.install`, `checks.test` или `checks.typecheck`. Одного поля `packageManager` для неё мало: команды npm работают и без corepack. Проверка запускает образ так же, как верстак: тот же пользователь, те же пределы, без сети, корень только для чтения. Нет ни программы, ни corepack — ошибка. В образе нет sh — ошибка: врач запускает команды через `sh -c`. В `packageManager` другой менеджер (команды зовут pnpm, а там `npm@…`) — ошибка: corepack откажется. package.json не разбирается — ошибка. Есть только corepack, а `packageManager` нет — предупреждение. Образа нет на сервере или он не запустился по другой причине — предупреждение.
  - **corepack не правит package.json копии.** Врач передаёт верстаку `COREPACK_ENABLE_AUTO_PIN=0`, и corepack не дописывает `packageManager` сам: в правке модели не появится лишняя строка.
  
  ### Как обновить приложение
  
  1. Обновить врача: на сервере перевести клон Ремонтника на метку новой версии и пересобрать (`docker compose -f deploy/compose.remontnik.yml up -d --build`).
  2. pnpm-приложению на `node:22`: в `remontnik.config` оставить или вернуть `workbench: { image: 'node:22', install: 'pnpm install --frozen-lockfile' }`, а проверки писать как обычно (`pnpm test`). Ни `corepack enable`, ни `corepack pnpm` в командах не нужно.
  3. В `package.json` приложения должно быть поле `"packageManager": "pnpm@<версия файла-замка>"`.
  4. Проверить внутри контейнера врача: `remontnik-doctor check-config` — в разделе «верстак» «pnpm в верстаке — через corepack».

## 0.1.6

### Patch Changes

- ed9ddca: - **Своё хранилище на сервере вместо GitHub.** origin врача может быть bare-репозиторием на том же сервере под пользователем git с git-shell. Врач ходит по SSH своим ключом: `REMONTNIK_GIT_SSH_KEY` (текст ключа, с `\n` или base64) и обязательная с ним `REMONTNIK_GIT_KNOWN_HOSTS`. Токен не нужен. Ключ живёт только в окружении врача и во временной папке контейнера (права `0600`). Хранилище держат `receive.denyNonFastForwards`, `receive.denyDeletes` и хук `deploy/git-update-hook`: метки `remontnik/**` не двигаются и не удаляются, а ключ врача пишет только в основную ветку и `remontnik/**`. У каждого ключа в `authorized_keys` — `restrict` и принудительная команда `deploy/git-shell-remontnik-git` с путями его хранилищ: ключ ходит только в них и только к git, без оболочки, scp и sftp. Хук и config принадлежат root. Рецепт — `docs/security.md`, «Своё хранилище на сервере».
  - **check-config для своего хранилища.** Для origin по SSH при заданном `REMONTNIK_GIT_SSH_KEY` вместо правил GitHub проверяет по SSH ключ и ключ сервера, настройки хранилища, хук, роль ключа врача, его привязку к хранилищу (проба в соседний путь должна получить отказ) и что пользователь git не пишет в config и хуки. Пробы ничего не записывают. Что хук и config принадлежат root, по SSH не проверить: всегда предупреждение с командой для root. С GitHub всё как раньше; origin по SSH без ключа врача — чужой хостинг, как раньше предупреждение «защита не проверена».
  - **Образ и compose врача.** В образе есть `openssh-client`, у контейнера врача — `extra_hosts: host.docker.internal:host-gateway`: так он доходит до SSH сервера.
  
  ### Как обновить приложение
  
  С GitHub:
  
  1. На сервере перевести клон Ремонтника на метку новой версии и пересобрать врача (`docker compose -f deploy/compose.remontnik.yml up -d --build`). Настройку и окружение не менять.
  
  Чтобы перейти на своё хранилище:
  
  1. Обновить врача, как выше.
  2. root на сервере делает хранилище, пользователя git и ключи по рецепту `docs/security.md`, «Своё хранилище на сервере»: хук и принудительная команда — из `deploy/` новой версии.
  3. Человек отправляет в хранилище код со своего компьютера: `git push` своим ключом.
  4. Закрытый ключ врача — в окружение врача `REMONTNIK_GIT_SSH_KEY` через `secret-handoff`, строка ключа сервера — в `REMONTNIK_GIT_KNOWN_HOSTS`. `REMONTNIK_GIT_TOKEN` убрать.
  5. `REMONTNIK_APP_DIR` заменить клоном хранилища (`git clone --no-local`, origin `ssh://git@host.docker.internal/<путь>.git`, владелец `10001:10001`). `REMONTNIK_UID` оставить `10001`. Межсетевой экран сервера должен пускать SSH из подсетей Docker.
  6. Перезапустить врача и проверить внутри его контейнера: `remontnik-doctor check-config` — ошибок нет, одно предупреждение про владельца хука; выполнить его команду от root.

## 0.1.4

### Patch Changes

- 39eb6af: - **Заголовки к поставщику модели в eval.** У поставщика `checks.eval.providers[]` есть необязательное поле `upstreamHeaders`: список `{ name, valueEnv }`. Нужно, когда сервер приложения достаёт до поставщика только через свой обратный прокси, а тому нужен ещё один секрет (например, токен прокси). `valueEnv` — переменная в окружении врача, как `keyEnv`. Значение ставит только прокси врача: одноимённый заголовок от eval не проходит, в eval, отчёты и журналы значение не попадает. Нельзя задать заголовки прокси (`authorization`, `x-api-key`, `api-key`, `proxy-*`, `host`, `content-length`, `content-type`, `cookie`, `forwarded`, `x-forwarded-*`, `x-real-ip`, `accept-encoding`, заголовки соединения). Нет переменной у врача — ошибка `check-config`, eval не запускается. Без поля всё как раньше.
  
  ### Как обновить приложение
  
  Если поставщику eval нужен свой заголовок:
  
  1. Поднять `@ykurilov/remontnik-watch` и `@ykurilov/remontnik-core` до новой версии точными версиями. На сервере перевести клон Ремонтника на метку новой версии и пересобрать врача (`docker compose -f deploy/compose.remontnik.yml up -d --build`).
  2. В `remontnik.config.ts` у поставщика добавить `upstreamHeaders: [{ name: '<имя заголовка>', valueEnv: '<ИМЯ_ПЕРЕМЕННОЙ>' }]`.
  3. Значение положить в окружение врача (файл окружения Ремонтника на сервере) под этим именем через `secret-handoff` и перезапустить врача.
  4. Проверить внутри контейнера врача: `remontnik-doctor check-config` — ошибок нет.
  
  Если заголовок не нужен — ничего не менять.

Запуск: `docker compose -f deploy/compose.remontnik.yml -f deploy/compose.remontnik.host-app.yml up -d --build`, второй `-f` — во всех командах `docker compose`. У сторожа `REMONTNIK_DOCTOR_URL=http://127.0.0.1:<REMONTNIK_HOST_PORT>`. Приложение в сети Docker — ничего не менять.

## 0.1.0

### Minor Changes

- a95d2c9: - `browser`: сетевой замок держится весь сеанс профиля — с первого вписанного пароля и до конца, в том числе после перезапуска службы (метка в папке профиля). Пароль, спрятанный страницей в `localStorage`, `sessionStorage`, `IndexedDB`, cookie или `window.name`, не уходит со следующей страницы. Выключить режим нельзя.
  - `browser`: новое поле политики `extraOrigins` — сторонние адреса страниц приложения (CDN, шрифты), открытые и после входа. Только подресурсы: переходы, фреймы и изменяющие запросы по-прежнему по `allowedOrigins` и `allowedMutations`. Точные origin `https://` или `http://`, без путей и масок, не внутренние адреса. Отказ в журнале службы называет сайт без поддоменов и подсказывает вписать его точный адрес в `extraOrigins`. WebSocket после входа — только к `allowedOrigins`. Неизвестные поля политики — ошибка.
  - `browser`: команда `remontnik-browser check-policy [путь]` проверяет политику без запуска службы.
  - `doctor`: `check-config` проверяет политику браузера через `docker exec` в контейнер службы браузера.
  - `browser`: после входа закрытый подресурс (счётчик, CDN) не роняет действие: снимок приходит с `blocked` — по строке на закрытый сайт с подсказкой про `extraOrigins`. На `fill-password` попытка унести пароль — по-прежнему отказ `refused_leak` с пометкой, что пароль вписан. Закрытый адрес не попадает ни в причины, ни в журнал; запись или сокет на другой сайт и пароль в адресе — событие журнала `leak_attempt`. Фильтр паролей ловит и base64 без учёта регистра, и base32.
  - `doctor`: модель видит только число закрытых запросов, отчёт о проверке страниц — сайты и подсказку про `extraOrigins`. `check-config` показывает не больше 10 ошибок политики короткими строками и называет настоящую причину, если проверка в контейнере не ответила.
- f0c536c: Первый выпуск набора самолечения приложений.
  
  - `core`: общие части набора и настройка `remontnik.config.ts` (`defineRemontnikConfig`).
  - `watch`: сторож внутри приложения — ловит падения, ошибки модели и инструментов, плохие ответы бота; шлёт случаи врачу и тревоги в Telegram.
  - `doctor`: врач на сервере — находит причину, правит в отдельной ветке, проверяет тестами и eval, выкатывает при зелёных проверках, следит и сам откатывает; переживает падения; команда `check-config`.
  - `browser`: по желанию — браузер врача для воспроизведения ошибок и проверки страниц.
  - `paseo-bridge`: по желанию — режим «сначала Paseo»: случай сперва уходит агенту проекта, врач берёт его сам, только если агент недоступен.
- 787ed76: Закрыты находки проверки безопасности.
  
  - `core`, `doctor`: полная память повторов отказывает (`503 replay_memory_full`), а не вытесняет старые метки; метку команды управления занимает только запрос, прошедший проверку роли; на `/v1/control/*` — не больше 60 чужих запросов в минуту с адреса (`429`); команды владельца предел не тратят; `signRequest` ставит ещё подпись заголовков без тела (`X-Remontnik-Head-Signature`, проверка — `verifyRequestHead`): по ней врач читает тело команды владельца мимо общих мест; чужие тела там читаются не больше 8 одновременно с адреса и 128 всего, лишнее вытесняет самое старое недочитанное чтение старше 2 секунд (вытеснить некого — `503 body_reads_full`), отказ без чтения тела освобождает место сразу.
  - `doctor`: общий секрет, секрет владельца и секрет моста — попарно разные и не короче 32 знаков; проверяют `check-config` и старт врача.
  - `paseo-bridge`: агент подписывает команды ключом задачи из письма, секрет моста ему не нужен. **Ломающее:** `remontnik-paseo` требует ключ — `REMONTNIK_PASEO_KEY` или `--key`. Ключ гаснет через 15 минут после итога (повтор итога до того — 409), через 24 часа после отмены и при новой задаче случая; у путей агента своя память повторов с квотой на ключ. Тип отчёта — внутри блока данных. Заголовки проверяются до тела, есть пределы соединений и время на заголовки.
  - `browser`: пока в контексте есть страница с вписанным паролем, соединения с адресами вне `allowedOrigins` закрыты во всём контексте (`refused_leak`). Решает прокси службы, через который идёт весь трафик Chromium: его не обходят ни `SharedWorker`, ни WebRTC, ни WebTransport; UDP мимо прокси закрыт флагами, имена хостов разрешает прокси; внутренние адреса (петля, частные сети, метаданные облака, IPv4 внутри IPv6) вне `allowedOrigins` прокси не пускает и без пароля (`refused_internal`), проверяя адрес после DNS и соединяясь на него же; прокси требует имя и пароль, свои на каждый запуск (`407`); одинаковые отказы сливаются, их число ограничено; живой экран принимает `POST` только со своей страницы, за прокси с TLS — и `https://<хост>`.
